## 结论与解释

- 本轮 45/45 通过功能验收。所有版本的基础提示词和工具定义哈希一致，控制审计无失败。
- A 的累计耗时、输入/输出 Token、未缓存输入、模型请求与工具调用均最低。
- 相对 A，B 累计耗时增加 21.35%，输入加输出 Token 增加 61.89%；C 分别增加 28.08% 和 42.42%。
- B 的单场耗时中位数略低于 A，不能把累计耗时最低表述为每个任务都更快。
- B 在跨文件修复和记录解析上较快，C 在算术修复上较快；A 的总体优势主要来自多模块任务。
- 15 组逐场配对中，B 比 A 快 7 组，C 比 A 快 4 组；没有进行显著性检验，不宣称总体统计显著。
- 36 个编码场次日志均可找到测试调用；测试与只读输入未被篡改。功能通过和存在测试调用不等于完整工程质量等价。
- 途中存在工具错误事件，各场最终恢复并通过外部验收；耗时和调用数保留这些开销。
- 本轮建议保留 A，不将 B/C 直接设为生产默认。不改变原先的极简理念：没有实测收益的精简不应仅因文字更短而采用。

## 限制

- 仅 5 类合成 Python/日志任务、每类 3 次；任务之间不是 45 个独立不同场景，不能外推到所有编程任务。
- 没有真实大型 Rust 开发、插件负载、长上下文压缩或恢复场景。
- 使用实际共享端点缓存，无法保证冷缓存；模型 ID 是代理端配置，未独立核验上游身份。
- B 同时改变长度和措辞，C 保留工具描述里的流程提示；不能把全部结果归因于长度或自主性单一因素。
- 代理费率未知，实际货币成本仍为 null；不使用其他端点的公开价格代算。

## 后续发现：换行混杂

在准备单句 A/B 复测时发现，旧运行器在 Windows 落盘提示词会把 LF 转成 CRLF，而 A 的默认编译常量仍用 LF；旧审计的文本读取又会归一化换行。原始计量与功能验收记录不变，但这不是严格只改变措辞的实验，不能将所有差异单独归因于提示词精简或流程自由度。本次新实验明确固定 LF，并用 Rust 公共接口和原始字节审计验证；旧实验目录与原始结果未改动。
