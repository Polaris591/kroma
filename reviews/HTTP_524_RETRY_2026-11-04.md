# SR-003 — Include HTTP 524 in bounded pre-stream retries

## Scope and evidence

Self-review of src/provider.rs (retry_delay and two regression tests). The
uncommitted model-catalog work is preserved and reviewed separately in SR-002;
there are no CI, dependency, protocol, persistent-schema or deployment changes.

The previous c07d13a repair covered connection failures, incomplete bodies and
keepalive-only streams before protocol progress. Its HTTP policy still allowed
only 429/502/503/504. The reported native-client error is produced by
ModelHttpError: a typed HTTP status, not an unidentified connection exception.

The new classification test was run BEFORE changing production logic and failed
with actual None vs expected Some(250ms), confirming the 524 omission.

Official interpretation (not proof of this user's specific gateway hop):
https://developers.cloudflare.com/support/troubleshooting/http-status-codes/cloudflare-5xx-errors/error-524/
The page currently states origin-response timeout, default 125 seconds, or a
proxy-write timeout. A client timeout increase cannot change that proxy limit.

## Findings

| ID | Severity | Location | Finding |
| --- | --- | --- | --- |
| SR-003-1 | medium | src/provider.rs:retry_delay | HTTP 524 was not in the transient status policy, so a gateway-origin timeout returned immediately instead of using the existing bounded pre-stream retry mechanism. |

## Dispositions

- SR-003-1: **fixed**. Admit exactly nonstandard status 524 alongside the existing
  statuses, preserving typed classification, Retry-After handling and caller
  progress guards. Do not make all 5xx errors retryable or parse error prose.

## Review notes

- Correctness: local HTTP mock covers 524 then success (2 requests), persistent
  524 (4 requests maximum), excessive Retry-After (1 request), and unsupported
  HTTP-date Retry-After (1 request). Errors do not leak into text callbacks;
  terminal failure retains typed HTTP 524. The existing begun-response/no-replay
  test also passes. No change to compatibility-fallback retry accounting.
- Readability/architecture: a single additional predicate in the existing
  provider policy, no new retry layer or helper abstraction.
- Security: no certificate bypass, endpoint rewrites, secret logging or replay
  of received protocol data. The mock is localhost-only with bounded socket
  reads/writes, explicit stop coordination and a total test deadline.
- Performance: existing maximum three extra transient retries remains intact;
  backoff is unchanged. This mitigates occasional failures, not a continuously
  overloaded origin. A retried request may still cause duplicate upstream work
  or charges; lack of client output is NOT proof of no billed work.
