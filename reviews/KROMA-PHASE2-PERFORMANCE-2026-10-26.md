# Kroma 第二批性能优化交付与验证（2026-10-26）

## 交付范围

1. **长会话写入**：`SessionStore` 使用 JSON 快照 + 检查和校验的 `.json.wal` 追加日志。每条用户、助手、工具消息独立写入、`sync_all`，不再每条都重写完整历史；压缩状态改动和日志阈值（256 条 / 16 MiB）触发快照。成功任务结束不强制快照。恢复校验完整行，丢弃未完成尾部，未得到确认的 Shell 结果标记为 unknown，绝不自动重放。
2. **超大工具输出文件**：取消或失败时通过 RAII 清理临时捕获；成功的大输出仍留在磁盘并由原始工具结果引用。新捕获按会话哈希前缀区分，只在启动时清理该会话超过 24 小时且未被会话引用的文件；`/clear` 会清理对应会话的输出。仍然引用中的文件不会按年龄清理；旧版本没有会话前缀的历史输出仍保留，以免误删。
3. **上下文构建**：对工具调用 ID 与命令执行一次前向构建，取代此前每个工具结果逆向查找、重复解析历史。

## 实测

- **磁盘**：约 4.2 MB 会话、连续新增 12 条工具结果，同台服务器 Rust Release 测得旧版每次全量保存合计约 **104–111 ms**；WAL 追加合计小于 **1 ms**（毫秒整数显示 0，不代表零耗时）。这是合成场景，不等于所有文件系统或所有消息大小的性能。
- **上下文**：3001 条消息、重复构建视图 8 次约 **13–15 ms**。新路径为线性前向映射，但小规模计时并不能证明真实端到端任务明显提速；TRC 候选优化仍可进一步剖析。
- **Rust 测试**：40 个正常测试通过，2 个手动性能基准默认忽略；Clippy `-D warnings` 通过，Release 构建成功。
- **真实模型**：DeepSeek 同轮返回三个独立 Shell 调用，2 次前台请求完成任务，三次工具结果和最终文件 CODE 核对正确。该会话的六条新消息保存在 WAL 中，可依据快照 + WAL 完整恢复，未触发 C 并发。

## 约束及待关注风险

- 与已定策略保持一致：**方案 B，顺序执行工具；首次使用工具输出的精确保守去重；缓存感知 TRC + 原始证据 APEC**。未加入 C 并发，也未收紧 Shell 凭据/权限。
- **一定同时备份 JSON 快照和 WAL**；成功任务后 JSON 快照可能滞后，只有经过 WAL 回放才是最新历史。模型上下文中的归档指针提供两者路径与消息序号。
- WAL 无加密、不是不可信磁盘文件的防篡改机制；校验用于检测损坏和截断，不代替用户文件权限。
- **超大输出仍被会话引用时不会自动删除**，这是为了保留原文；长期会话原始输出仍可能积累。
- Windows 文件同步与大量长历史压力未在此轮验证；建议公开跨平台交付前补足。
- 当前 Git 仓库尚未建立首次提交；将来应先建立可追踪版本基线。
