# Kroma 已发现问题与修复设计

## 1. 范围、结论与证据

本方案基于当前工作树的源码复核和隔离探针，目标是修复已发现的问题，而不是重写 Agent。

- 没有开启子代理，没有修改生产代码。工作树原有修改保持不动。
- 本轮补充了审查探针及本文档。完整逐模块、逐功能审查尚未结束，未列出问题不表示该模块已被证明无缺陷。
- 共整理 16 项缺陷/功能缺口及 4 项设计取舍或待量化改进。严重度与修复顺序分开：网络问题直接影响当前使用，应尽早修复，但不能据此夸大为安全漏洞。
- 下表“复现”表示执行到了真实生产代码路径；“源码”表示代码机制已确认、尚未专项复现；“设计”不是现有行为必然错误。
- 原始网络探针模拟的是 HTTP 响应体提前关闭，不是用户真实上游的 TLS/10054 现场。对端、代理、网关谁发起断连仍未确定。

## 2. 修复必须维持的不变量

1. WAL/原始历史是事实来源；请求预算、展示截断和协议转换只改投影。
2. 已完成工具结果不自动重放；未知结果不伪装为成功或明确失败。
3. 工具调用和对应结果必须闭合，压缩不得切断调用/结果组。
4. 取消必须停止当前受管进程树，不能因为“网络恢复”自动复活已取消任务。
5. 失败、重试、未知计量都必须如实可见，不把未知成本记作零。
6. 不增加任务步数上限。限制单次读取、单个响应和瞬时队列，不等于限制任务能执行多少轮。
7. 不全局放开 TLS 检查、不忽略传输错误、不用字符串匹配猜错误类型。
8. 不引入新数据库、通用调度框架、全局重试器或万能插件安全框架。

## 3. 网络与任务恢复：问题 3、17、18

### 3.1 根因要分成两层

外部层：连接异常结束，具体可能在服务端、代理、网关或本地网络。TLS close_notify 缺失和 10054 本身不能证明 Kroma 主动断开。

Kroma 层：错误分类只覆盖 timeout/connect 和有限的瞬态 HTTP 状态；响应体阶段的连接重置、提前 EOF 可能漏出重试。同时用非空 chunk 充当“已经取得不可重放的生成进度”。

因此，不应承诺“加一个 keepalive 就根治网络错误”，也不能简单写成 `is_body() || is_decode()` 全部重试。

### 3.2 先修首字节前的错误分类

在现有 Provider Module 内，以稳定错误种类记录失败阶段、原始 cause、生成进度、可用用量。不要把 source chain 格式化为字符串后丢掉；Agent 不解析错误文案来决定重试。

分类至少区分：

- 建连/传输超时；连接 reset/aborted/broken pipe；传输提前 EOF/不完整响应体。
- TLS 证书、主机名、验证失败：不自动重试，不关闭验证。
- HTTP 状态失败：沿用明确的暂时性状态策略。
- SSE/JSON/工具参数语义非法、资源超限：不当成网络抖动反复重试。
- 明确取消：立即退出，不重试。

重试策略：保持最多 3 次额外瞬态重试；退避可采用有上限的指数退避和抖动；尊重 Retry-After，不因过长或不认识 HTTP-date 就提前重试。取消必须能中断等待。协议兼容降级与传输重试使用明确的独立预算，并仍有总尝试次数上限。

### 3.3 再细化生成进度，不直接替换为“屏幕没有文字”

| 进度 | 自动重试策略 |
|---|---|
| 尚无响应体、无生成进度 | 符合暂时性分类时允许 |
| 仅收到完整识别的 SSE 注释/无业务语义心跳 | 可以允许，但需修改现有“任何字节后不重试”的文档及回归测试 |
| message_start / response.created 等起始事件 | 默认保守；可能含请求 ID、用量或服务端生成状态，不能一概忽略 |
| 文本、推理、工具调用片段、原生续接数据已有进度 | 不自动重放整个请求 |
| 收到有效协议终态 | 按该协议完成条件完成，不硬性额外要求所有协议都有 [DONE] |

不能只看 UI 是否打印文字：推理、工具调用和签名状态也有意义。一个跨多个 chunk 的未知半截事件也不能先假定是无害心跳。

每次尝试独立持有解析器和暂存状态；重试前清掉旧暂存，不能把两次响应拼成一条。已知上游用量及未知尝试数另行累计。

没有上游幂等能力时，只能保证不重复本地已执行工具，不能保证服务器只生成一次或只收费一次。不要擅自给所有供应商套用同一种幂等键语义。

### 3.4 Keepalive、连接池与诊断

- 保留当前 20 秒建连、300 秒头部/分块空闲策略；不要加覆盖整个健康长流的短总超时。
- 评估显式 TCP keepalive 和连接池 idle 参数，使用跨平台支持的配置。未显式设置不等于 reqwest 没有默认连接池回收。
- 保活只能辅助发现死链，不能保证绕过代理的应用层无输出超时。
- 不为所有失败都重建 HTTP Client；是否与复用旧连接有关，先通过可控对照诊断。
- 记录尝试序号、失败阶段、进度状态、距最后网络数据的时间、已知用量；不记录密钥、完整请求正文或带凭据 URL。

### 3.5 部分流后的恢复

第一阶段维持现在的安全默认：保存失败说明，不把半截回答保存为完整 assistant，不自动执行半截工具调用。

改善 UI：明确显示“部分回答未完成、已完成工具保留”，提供“从已保存状态继续”，不要要求用户猜测是否重跑。

若以后提供自动续接，应是单独可选策略：以已持久化状态发起新一轮，不重放旧工具调用；尝试有界，遇到未知副作用或取消即停止。即便如此，也不能保证模型不会提出新的等价副作用操作；外部幂等和人工确认仍有必要。

### 验收

- HTTP 200 后零字节断流，第二次成功：正确重试；连续失败不超过预算。
- 连接 reset、提前 EOF、超时；401、证书错误、非法 JSON、资源超限：分别断言请求次数。
- 只有注释心跳后断流；message_start 含用量；只产生 reasoning；只产生工具参数：验证策略差异。
- 退避期间取消立即停止；已完成工具只运行一次；故障后重启不重放未知工具。
- 健康长流可超过普通请求总时长；空闲流仍按 idle deadline 退出。
- 实际 TLS 截断需另加可控 TLS 夹具；现有 HTTP 探针不能替代它。

## 4. 项目代码授权：问题 1、2、8

### 4.1 插件代码指纹

把用于快速热更新检测的元数据，与用于授权的内容摘要分离。

- 授权必须读取实际入口的字节，与扩展名、长度、mtime 无关；Python、PowerShell、Shell、本地二进制等显式入口同样处理。
- 使用密码学内容摘要；优先复用仓库已有 SHA-256 能力并验证已知向量，不再用 FNV/长度充当安全授权标识。
- 摘要材料明确编码版本、规范路径、manifest、执行参数和被承诺覆盖的代码集合，字段之间采用无歧义编码。
- 单文件、总字节、文件数量均受限制；读取失败、扫描截断、超预算不能静默继续授权或用空字节替代。
- 加入/删除被覆盖文件同样改变授权结果。热重载及启动新 worker 前重新验证；拒绝加载不影响其他已成功加载模块。
- 使用新指纹格式时，旧项目授权需要显式重新确认，不偷偷升级为可信。

### 4.2 MCP 依赖扫描

短期确定性修复：扫描被接纳文件的完整内容，预算沿用已有每文件/总大小限制；如果另设扫描预算，到达预算必须明确拒绝自动认定“内容未变”，不能只扫前缀后继续给出可信结果。

中期把授权范围显示出来：已覆盖入口/相对依赖、明确未覆盖的 bare packages、运行时计算路径、项目外文件。支持显式声明额外授权文件；必要时拒绝这种配置或要求用户选择更宽的信任范围。

静态字符串扫描不能证明任意 JS/Python/Shell 的完整动态依赖。扩大扫描前缀或改成 AST 也不等于沙箱。若要保证运行内容等于批准内容，需要受控不可变执行副本或更强运行环境，不能在当前轻量修复中虚假承诺。检查到启动之间的并发改写同样属于需要声明的 TOCTOU 边界。

### 4.3 状态只有一个实际来源

插件展示区分：用户想启用、当前已授权、实际已加载，以及阻止原因。最小兼容做法是 `enabled` 表示实际可用，另给 requested/approval/block reason；若旧调用方把 enabled 当用户选择，需用新增字段过渡。

禁止列表再独立推算一次与运行时不同的启用结论。

### 验收

- 等长、相同 mtime 的非 JS 入口修改必须失效；删除、替换、重命名也覆盖。
- 原探针中放在 2 MiB 之后的相对 import，其依赖变化必须要求再批准。
- 超预算、无法读取、符号链接/目录联接循环：行为有界、拒绝原因明确。
- 列表显示因“代码变化”阻止，不再显示工具已经生效。
- 旧批准记录不能误匹配新格式；批准及撤销继续使用现有跨进程锁。

## 5. 分叉及上下文恢复：问题 4

缩短历史时应丢弃指向未来的派生摘要，但不能同时忘记仍保留的已确认消费前缀。

- 整段复制保持原状态；空历史恢复初始状态。
- 部分裁剪清除不再适用的 summary/TRC 索引和测量缓存。
- 已消费边界先取原确认边界与保留长度的较小值，再按完整协议组校验/收缩；不能直接把 retained.len() 标成已消费。
- 若旧数据没有可靠边界，按已有完成请求/完整调用组重建，不从未知工具结果猜测成功消费。
- 继续验证 covered_until <= consumed_until <= retained.len()。
- 原生 reasoning 的 revision/provenance 必须跟随新投影失效规则，不能复用被裁剪未来的签名。
- 外部 Context Adapter 仍须显式支持裁剪；不支持时保持原会话不变，不静默清空自定义记忆。

原单条巨型输入探针混入了“源文本自身装不进摘要窗口”的因素。本轮新增多轮对照已经证明独立的边界问题：恢复确认边界后 prepare 成功。但这不意味着任意超大单条用户输入都能自动压缩；无法装入仍应明确拒绝，不能偷偷删原文。

验收：多轮长历史 fork/rewind/undo 后可继续；单条超窗仍诚实失败；完整复制不变；并行工具结果组不被切断；未知结果不被标成已消费；提交失败不修改原状态。

## 6. 事务与计量：问题 5、6、15

### 6.1 Profiles

提供“更新事务”而不只给 save_at 最后一段加锁：规范化目标路径 -> 获取跨进程锁 -> 重读最新内容 -> 应用单次变更 -> 校验 -> 私有临时文件 -> 原子替换 -> 同步 -> 释放锁。

复用现有 catalog_file 的锁与原子写机制，避免第二套锁协议。所有 CLI 和桌面修改入口迁移到同一事务路径。

交互式询问不持锁；先收集用户输入，再提交目标配置的变更。不同 profile 可以合并；同一个 profile 基于过时内容修改时检测冲突并提示，不用完整旧快照覆盖最新文件。保留用户配置符号链接行为；锁应对应规范目标，避免不同路径别名绕过锁。

公开的整份快照保存接口若保留，明确它是整体替换而非并发合并；不能自动把任意两份配置猜测合并。

### 6.2 桌面用量持久化

最小修复保证：写失败后待保存数据仍在；刷新操作串行化；成功后才确认该批次。

正确的提交单位是增量批次，而不是先读取总量再另一次 set_usage。读取最新账本和应用增量必须在同一个现有 catalog 事务内，避免覆盖期间其他来源的更新。

还要处理“替换成功，但目录同步报错”的不确定提交：每批次有稳定 ID，账本原子记录已应用批次，重试同一批次不能重复计数。不能简单在所有 Err 后原样塞回再加一次。

记录中绑定 session，避免切换后把旧请求计到新会话。不要持 UI 事件锁做文件 IO；发送新用量与刷新互不长期阻塞。

保证范围必须写明：未持久化的观测仍可能因进程崩溃丢失。若要求这些也恢复，需要持久 outbox/usage receipt；不要把内存重试说成崩溃级 exactly-once。用量侧车失败不能破坏会话原文。

### 6.3 摘要失败的计量

每次真正发起的请求有独立尝试记录。已知 token 保留为已知部分，后续未知尝试增加 unknown 计数，不把整个累计结果抹成 None 或零。

优先利用已有 UsageMeter 的分字段已知/未知能力：摘要错误携带请求次数和已观测计量；成功、失败、取消、终态统一结算，防止重复。

只给最终 Err 加字段不足以覆盖外层 timeout 丢弃 Future：累计记录必须由调用者持有或在每次尝试完成时上报。未提供计量的外部后端仍保持 unknown，不要求所有插件马上升级协议。真正开始请求之前的 payload 构造失败不伪造已发出的 HTTP 请求。

验收：两个写入者更新不同配置都保留；同项冲突可见；锁占用不无限等待；存储失败后恢复补账；重复刷新/不确定提交不双计；已知 100/10 后再遇 401 或 timeout，仍显示已知部分和未知状态。

## 7. 进程生命周期与 IO：问题 9、10、12、13、14

### 7.1 Windows Job

保留 KILL_ON_JOB_CLOSE 和取消时 TerminateJobObject。删除“超 128 自动关闭最老活动 Job”的驱逐策略。

定期查询 Job 活动进程数：空 Job 可以关闭；仍有后台进程的 Job 保留到 Kroma 退出。活跃后台任务数量本身是用户产生的资源，不应借句柄回收静默终止。如果产品需要硬限制，应在启动前明确拒绝或提供用户清理命令，而不是事后杀任务。

FFI 留在 winsys，查询失败采取不误杀的保守策略，补充 SAFETY 说明。

验收：启动后台心跳后运行超过 128 个普通命令，心跳仍在；取消当前任务不误伤先前成功后台任务；Kroma 退出/被强杀时包含的子进程仍按原承诺终止。

### 7.2 /diff

迁移为可取消异步命令，直接传 argv，不经 Shell 拼接。复用现有受管进程树机制。stdout/stderr 有界读取并继续适当排空，避免管道死锁；达到显示上限明确标记截断，必要时提供文件引用。可给这个只读 UI 操作独立、明确的等待策略，不改变一般 Shell 默认无限时运行的约定。

仅 spawn_blocking 包住 .output() 不算完成：调用者取消后，后台线程/进程仍可能继续。

验收：假 Git 卡住时界面仍响应取消且子进程停止；巨大 stdout/stderr 不完整缓存在内存；Unicode、无 HEAD、Git 错误保持合理行为。

### 7.3 进程模型流

在现有进程 Adapter 中加入请求累计字节上限，可与 HTTP 的 64 MiB 策略对齐。累计文本、推理、工具参数及最终 completion，追加前检查；有界帧队列不等于最终聚合字符串有界。

超限为明确资源错误，取消 worker，不作为暂时性网络错误重试。单帧、调用数量、参数大小等已有校验保持。

验收：大量小合法帧仍会到达总限制；恰好在限制内可完成；文本/推理交替不能绕过；最终帧绕过增量也受校验；超限后无遗留进程。

### 7.4 Shell 预览

对快照计算出的区间做 `take(size - start)` 有界读取，而非 read_to_end。偏移按实际读入字节更新，不能读到快照之后的新数据却只前移到旧 size。保留全部原始文件，不因预览限制截断真实输出。

验收：文件在 metadata 之后增长，本次仍不超过预览窗口；下次不重复已展示部分；短读/截断/多字节字符边界不 panic。

### 7.5 附件

统一在读取操作上限制 limit + 1，而非只检查 metadata。普通文件类型校验尽量基于已打开句柄，读取后再验证实际长度；图片、日志、普通导入使用各自现有上限。

读取和大块编码从 UI/异步事件处理线程移走；必要时限制同时处理数量。超过限制不继续分配完整文件，明确提示以引用方式使用，不偷偷发送部分图片。

验收：文件检查后增长、超大图片、伪造 bytes 元数据、非 UTF-8 日志等均有界失败；合法附件格式和图片缓存行为不变。

## 8. 协议与桌面宿主：问题 7、11、16

### 8.1 合法工具调用的共同校验

在适配器返回给 Agent 之前统一校验：assistant 角色、非空唯一调用 ID、非空工具名、合法 JSON 对象参数、正确工具种类及合理资源边界。复用最小的规范化检查，不复制四份规则，也不强行把供应商原生 payload 统一成一种结构。

Responses 的 opaque reasoning、Anthropic 的原生 block 顺序和签名继续由各 Adapter 维护。不对供应商所有未知扩展字段一刀切拒绝；需要统一的是会进入执行/持久化的共同语义。

验收：Chat/Responses/Anthropic/进程模型同样拒绝数组、标量、空 ID、空名、重复 ID；合法原生续接不退化；不合法消息在落 WAL 和执行工具之前被拒绝。

### 8.2 真正有界的桌面事件

同时限制条数、总字节、单事件大小。同步 EventSink 不能因 UI 停止消费而阻塞 Agent。

呈现增量可以合并；队列溢出后标记 resync_required 并暂停继续堆积，保留固定大小的最新任务终态。工具状态属于可由 WAL 重建的呈现信息，不必无界保留每个中间状态。计量从呈现队列独立聚合，不能因丢展示事件丢账。

UI 恢复后利用现有分页快照重建可见历史；不能为“补齐事件”一次加载无限历史。用户应知道实时画面暂停但任务仍在运行。参考 TUI event_queue 已有预算与恢复策略，不为此引入泛型事件总线。

验收：混合推入大量状态/增量/超大事件，条数和内存预算都不超限；末态可见；恢复后与 WAL 一致；计量不因展示丢弃而变化。

### 8.3 桌面队列

最小正确修复：在没有消费者前让接口明确返回“尚不支持”，而不是假成功。

若按 CLI/TUI 功能对齐：由现有宿主执行循环串行消费 followups，不增加另一个 Agent 或全局后台调度器。成功后运行下一项；失败/取消暂停队列，提供查看、清空、显式恢复。每轮复用同一个受控 runtime，确保所有退出路径还原宿主所有权。

任务完成事件与整个宿主执行 done 的语义必须区分清楚，防止前端显示空闲、后端仍占用 runtime。队列必须与会话绑定；切换/关闭时给出明确去向，不能把旧队列送入新会话。

验收：队列顺序、运行中追加、失败暂停、取消暂停、恢复、不支持路径及会话切换都覆盖；没有任务被静默吞掉或重复执行。

## 9. 不默认改变的取舍：问题 18、19、20

- 部分流自动续接：默认关闭；先改错误说明和手动恢复，不把网络修复变成副作用重放。
- Steering：维持现有“本批次完整闭合后生效”的测试契约，UI 明确提示生效时间，紧急停止使用取消。若另增“下个工具前中断批次”模式，必须显式设计：不重跑当前工具，为明确未执行的剩余调用写 skipped（不是假成功，也不是未知），持久化后再送新指令。该行为不能悄悄替换现有默认。
- 性能：先测每轮 prepare/投影/预算/序列化耗时及分配，再消除同一投影的重复工作。缓存键必须含上下文 revision、模型/协议、工具 schema、动态 prompt、附件模式等实际影响项；不能为少一次 clone 就修改原始历史或沿用错误 token 测量。没有测量前不宣称固定几倍加速。
- 不增加 max_steps；可提供观测或用户选择的预算策略，但不偷偷引入硬停轮数。

## 10. 架构收敛及交付顺序

已有的 Module 应加深 Implementation、收敛 Interface，而不是增加一圈包装：

- Provider Module 在 ModelBackend Seam 后隐藏传输分类、SSE 进度与重试；各协议 Adapter 只承担协议差异。Leverage 是调用方不用理解具体网络错误，Locality 是重试规则在一处。
- 授权 Module 内分开“热更新元数据”和“批准内容”；插件与 MCP 只共享确有重复的文件摘要/有界读能力，不建立万能 TrustEngine。
- 持久化沿用 catalog_file 事务 Seam；配置与用量的业务合并规则仍在各自 Module，不引入通用 Repository 层。
- 宿主保留自己的呈现 Adapter；桌面/TUI 分享有界与重同步策略，不强行共享所有 UI 类型。

| 批次 | 交付内容 | 重要约束 |
|---|---|---|
| A | 首输出前断连分类与回归；插件/MCP 授权缺口 | 小范围修复，先守住不重放与不误授权 |
| B | 心跳进度策略、网络可诊断性、分叉消费边界 | 更新明确的行为契约；不把协议起始帧统一忽略 |
| C | Profiles 事务、桌面用量失败保留与幂等、摘要失败计量 | 避免“修丢账引入双计/覆盖更新” |
| D | Windows Job 生命周期、Shell/附件/进程流资源边界、异步 diff | 保持取消和原始输出完整性 |
| E | 工具调用共同校验、桌面事件重同步、队列明确支持状态 | IPC 字段采用兼容迁移；不伪装已实现 |
| F | 可选自动续接、可选 steering 模式、经过基准验证的优化 | 不混入可靠性热修复，单独确认产品行为 |

每个问题独立小提交，连同可失败的回归测试交付；不要一次把所有模块重构后才验证。安全修复需要版本化授权迁移；持久化格式新增字段保持旧数据可读；任何修改失败原会话保持可恢复。
