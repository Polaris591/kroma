## P0：凭据与工具执行边界

### R-01：Shell 默认继承 Kroma 自身的 API 密钥环境变量

**证据**：src/config.rs:30 从 KROMA_API_KEY 读取凭据；src/shell.rs:136 创建子进程，未对敏感变量调用 env_remove / env_clear。Rust 子进程默认继承父进程环境。

**风险**：通过 shell 执行的模型指令可以读取环境中的 KROMA_API_KEY 及其他进程环境凭据，敏感值可能回流到模型请求、日志，或被恶意提示注入指令带走。由于工具本身允许执行用户权限下的任意 Shell，此处不是完整隔离沙箱；单纯剥离几个环境变量也不能保证高权限进程的机密完全不可访问。

**验证状态**：源码明确支持此结论；未进行真实凭据读取或外传实验。

**建议**：先针对 Kroma API 凭据做最低限度的子进程环境剥离与回归测试；明确文档中的信任边界。若将来支持不可信仓库/远程用户，单靠 env_remove 不构成完整隔离，需另行决定凭据代理或进程隔离。不要强制改变现有任意 Shell 命令的产品理念。

**验收**：使用假密钥测试：模型 Shell 无法通过普通环境变量读到 Kroma 自身的 API 凭据；模型 HTTP 请求仍能正常认证；普通开发环境 PATH/HOME 等不受影响。

## P1：正确性、失败恢复与长期运行

### R-02：规则输出过滤会删除语义关键行（已复现）

**证据**：src/tool_output_filter.rs:155（is_routine）将 INFO、DEBUG、building 等行视为常规日志；src/tool_output_filter.rs:191（filter_stream）对未命中错误/摘要关键词的例行行执行删减。

**独立复现**：构造成功的 cargo build 工具结果，原始 20,358 字节，在例行 INFO 行写入关键标记 KEEP-2026-EXACT；调用生产过滤函数后投影为 954 字节，归档指针存在，但精确标记不再出现于模型可见输出。

**风险**：标记、路径、设计决定、隐含警告可能藏在被标为“常规”的日志中；模型不能从未见过的内容中恢复正确细节。虽然原文仍保存在会话文件里，模型并不一定意识到需要回读。

**建议**：保守过滤而非增强关键词抽取。优先移除宽泛 INFO/DEBUG 直接删除规则；将删减目标缩为能严格识别的重复、进度百分比、终端动态刷新等模式。对于未能确证为纯噪声的文本，默认原样放行。

**验收**：加入含随机非关键词精确标记的编译成功/失败、测试、安装、源码读取、普通日志夹具；任何语义独特行都不被丢弃；真实样本再测净 Token 收益。

### R-03：APEC 失败后可能无法在同一状态修订版本自动重试

**证据**：src/compression.rs:494-495、534-537 在 failed_revision 等于 state.revision 时禁止启动；src/compression.rs:580、588 等出错路径将 failed_revision 设为当前修订号。

**风险**：一次瞬态超时、上游 5xx、摘要太长或失败后，后续请求未必改变压缩修订号。这样同一进程会持续阻止摘要，直到其他状态变化、重置或重启。到硬阈值时可能无法推进任务。

**验证状态**：源码路径确认，尚缺故障注入的端到端回归测试。

**建议**：有限冷却与有限重试，失败不能永久锁住可恢复工作。避免在用户每轮对话都无限烧钱重试；硬阈值优先报告精确错误及可恢复动作，不丢原始历史。

**验收**：第一次摘要返回模拟 5xx/超时、下一次恢复成功；不清会话、不重启即可在合适时机恢复；持续失败不会无限调用。

### R-04：每个工具结果都全量重写 JSON 会话并 fsync

**证据**：src/agent.rs:147-151 每条顺序 Shell 结果触发 SessionStore::save；src/session.rs:159-203 每次克隆全部消息、JSON 序列化、创建临时文件、sync_all 并 rename。

**风险**：长会话会造成随历史长度持续增加的磁盘写入、序列化和延迟；方案 B 同一轮三个工具结果，也仍然触发三次全量重写。总历史不断增长时，累计 I/O 近似二次增长。

**验证状态**：静态代码路径及算法复杂度确认；尚未进行大历史负载对比。

**建议**：先采样不同会话大小下的保存耗时与磁盘写入量。随后评估最小变更的追加日志/检查点或批次落盘方案；取消/崩溃必须仍能确定每个工具是否执行。不要立即引入重型数据库。

**验收**：1MB/10MB/100MB 历史下的操作耗时和总写入量；B 批量执行、Ctrl+C、进程崩溃后恢复不重复执行可能有副作用的命令。

### R-05：大工具输出文件与取消后的捕获文件缺乏生命周期管理

**证据**：src/shell.rs:100-121 仅小结果删除捕获文件，大于 1MiB 的捕获文件长期保留；src/shell.rs:133-166 取消或启动失败可能在执行结果读取之前留下捕获文件。

**风险**：长时间执行构建/测试，磁盘可能逐步被历史工具输出占满。用户即使 /clear 会话，也没有对应的文件清理路径。

**验证状态**：源码确认，未做累计磁盘压力测试。

**建议**：记录工具捕获文件的归属、保留量和清理条件；默认保障会话可追溯，同时允许有明确上限/配额的安全清理。不要为了省磁盘而悄悄丢弃唯一证据。

**验收**：高输出、取消、启动失败、/clear 后文件生命周期可预测；不误删仍被活跃会话引用的文件。

### R-06：模型请求投影对长历史有重复扫描和重复解析

**证据**：src/compression.rs:403 的 view_with_state 对每个 tool 消息重新向前扫描 messages[..index] 寻找对应调用，并反复 JSON 解析参数；trc_plan 多次构造整个 view、序列化估计 token。

**风险**：长会话和大量工具返回时出现明显额外 CPU/内存开销，影响低延迟目标。

**验证状态**：算法复杂度明确，尚无隔离 benchmark。

**建议**：每次构造请求视图时建立一次 tool_call_id -> command 映射；过滤投影可复用稳定结果；避免在 TRC 每个候选下全量重建不变部分。先性能测量再做有限优化。

**验收**：100/1,000/10,000 条历史消息时的视图构造耗时、内存与 Token 投影完全一致。

## P2：兼容性、可靠性、可观测性、测试

### R-07：小体积二进制/非法 UTF-8 输出不再逐字节保真

src/shell.rs:100-108 将小于等于 1MiB 的输出转换为 String::from_utf8_lossy，然后删掉原始文件。对于二进制/非法 UTF-8，原始字节因此无法恢复。应更新“所有字节均保留”的文档承诺，或设计低成本二进制保护路径。构建日志纯文本场景不一定受影响。

### R-08：命令完整明文日志可能暴露敏感参数

src/agent.rs:169 将完整 Shell 命令输出到 stderr。用户传入带令牌、密钥或私密 URL 的命令时，这些值可能留在终端/进程日志。建议对高风险参数做轻量脱敏或可控展示，不应对普通调试命令完全隐藏。

### R-09：模型提供方兼容性回退不足

src/model.rs:439 始终请求 stream_options.include_usage；部分 OpenAI 兼容端点不支持该字段。HTTP 错误直接结束任务。建议在确认请求明确因字段不支持而失败时提供一次兼容回退，且不能掩盖其他 HTTP 错误。真实 DeepSeek 通道可用不代表所有提供方兼容。

### R-10：Token 预算及成本核算仍有不确定性

src/compression.rs:891 使用 JSON 字节数/3 的粗估，靠 API 用量向上校准；对不同语言/模型 tokenization 的准确性尚未验证。TRC 使用假设的缓存优惠和未来调用数，非真实报价。APEC 失败和超时可能产生未进入成功摘要统计的使用量。

建议保留“估算与未知”标记，增加边界样本和上游拒绝后的恢复测试。不要宣传已精确优化货币成本。

### R-11：缺少整体资源预算和失控循环防护

Agent Loop 刻意不设固定步数，Shell 也无执行超时；符合用户希望 Agent 自由运行的设计理念，但无人值守任务可能无限循环、消耗大量 API/磁盘资源。建议提供可选且简单的用户预算/取消保护，而不是默认强制上限或复杂审批模式。

### R-12：Windows 子进程取消语义不完整

src/shell.rs 对 Unix 创建独立进程组并发送信号；Windows 只有 kill_on_drop，未实现可靠的子进程树清理。README 已承认这一差异。若要公开支持 Windows，必须在 Windows 上实测取消子进程/后台任务。

### R-13：流式协议、工具调用关联和异常恢复测试不足

src/model.rs 提供了一些 SSE、Delta 和 usage 单测，但没有完整覆盖重复 ID、异常索引、截断与 [DONE] 的边界组合。src/session.rs 的中断恢复只有一个工具调用的测试，没有三个工具执行到第二个时崩溃并恢复的测试。建议新增端到端 mock provider 与工具序列测试，涵盖异常、取消与恢复，不需要引入新的运行时架构。

### R-14：尚无版本基线、CI 与可复现 Review diff

当前 git status 显示所有源码未跟踪，分支 master 还没有第一个 commit；无可见 .github 工作流。即使 28/28 测试通过，也没有可靠的版本比较、回滚和变更归因。建议先建立受控的首次提交，并使用轻量 cargo fmt/test/clippy/build CI。提交前确认 .env、凭据和实验日志不会入库。

### R-15：文档存在历史描述与现行行为不完全一致

README 中 TRC “模型首次见到的结果完整”措辞与首轮规则式过滤并不完全一致；旧 benchmark 脚本仍使用已废弃的 KROMA_TOOL_EXPERIMENT / KROMA_FUSION_EXPERIMENT，不能据此重跑旧策略。建议修正文案或明确归档；不需要保留两套生产逻辑。

## 正向评价

1. 方案 B 的落实足够简单：提示词只施加于模型请求视图，恢复会话不会重复追加；多工具调用与 tool_call_id 正确配对；生产代码无并发调度器。
2. 原始会话与投影视图分离；APEC 摘要从原始历史取证，保留了比关键词证据投影更安全的记忆路线。
3. 硬上下文阈值拒绝不安全继续发送，而不是静默丢弃历史。
4. Unix Shell 取消有子进程组清理，并有基本回归测试。
5. HTTP 客户端已限制超时、对部分超时重试防止重复用户可见输出，SSE、缓存统计与摘要开销有基本观测。
6. 源码总规模不大，没有必要为了“模块化评分”把现有工程立即重构成插件微内核。

## 建议执行顺序（不改变已定设计）

**第一批：正确性与机密保护（优先）**
- R-01：工具子进程凭据隔离与假密钥回归；
- R-02：规则过滤保守化，并验证精确事实不丢；
- R-03：APEC 有界恢复与故障注入测试；
- R-13：至少补批量工具的崩溃/取消恢复测试。

**第二批：长时间运行效率**
- R-04：先测会话全量 fsync 写入成本，再做最小的持久化优化；
- R-05：工具输出文件生命周期及清理；
- R-06：线性化工具命令映射，减少重复 JSON/视图构造。

**第三批：交付与兼容**
- R-07/08/09/10/11/12：视真实产品目标逐项处理；
- R-14：首次干净版本提交与轻量 CI；
- R-15：更新事实描述与归档实验脚本。

**不建议做**：重新启用 C 并发、引入新压缩策略、把单文件原型重写为大型框架、加入强制审批/非 root 配置、为当前短历史提前引入数据库。这些工作没有与本次审查发现的实际风险形成有利的成本收益比。

## 完成标准
