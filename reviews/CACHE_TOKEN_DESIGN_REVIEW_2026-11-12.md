# Kroma 缓存与 Token 设计深度审查

日期：2026-11-12。基线：HEAD `d6aa128` 加审查时的未提交工作树。

## 结论

**不能认定是“目前最棒”。更准确的评价是：主干策略合理、证据保护和用量诚实性较好，但插件投影、最终请求可观测性、缓存写入成本以及跨协议缓存策略还没有闭环。**

本次发现一个离线确认的请求前缀问题：插件参考资料每次追加在请求末尾，下一轮被新模型消息/工具结果挤到后面。原始历史没变，不代表上一份已发送请求是下一份请求的前缀。现有测试通过，并不能覆盖这个不同的不变量。

本次不修改生产逻辑、用户配置、真实会话或已安装程序，不调用付费模型。结论适用于所审查的源码工作树，不代表正在运行的二进制。

## 1. 必须区分的目标

1. **上下文容量**：某次请求实际占用多少上下文。缓存命中的输入仍占上下文，不等于消失。
2. **累计 token**：完成整个任务的主请求、重试、续写、检查点、标题以及可观测辅助调用的累计输入/输出。
3. **实际费用**：区分未缓存输入、缓存读取、缓存写入及其 TTL、输出、服务端工具费用。
4. **质量和延迟**：任务是否正确完成、是否需要重新读证据、首 token 与任务完成延迟。

少发字不必然少付钱；高缓存率也不必然便宜。更不应通过少验证、丢证据、隐藏失败或强制换模型来省表面数字。

## 3. 发现与优先级

### F1 — 高优先级：插件参考资料不满足已发送请求的 append-only 契约

**证据：** `src/plugins/model.rs:636–646` 的 `with_packs` 每次克隆原始投影，再 `view.push(reference)`。该 reference 不进入原始历史，下一轮重新生成。

当模型调用工具时，真实顺序为：

```text
第 1 次发送：system, user_A, memory_A
第 2 次发送：system, user_A, assistant(tool_call), tool_result, memory_A
```

第一份请求中第三条是 `memory_A`，第二份请求中第三条变成模型消息。即使 memory 字节完全没变、system/tools 也没变，**前一份完整请求不是后一份的前缀**。跨用户任务同样如此。

**离线验证：** 在系统临时目录中原样提取当前生产 `with_packs` 函数，直接导入生产 `src/protocol.rs` 的 Message 类型。两个新增探针确认：

```text
tool-loop: prior sent messages=3, common prefix=2,
           first changed old role=user, new role=assistant
new-user: prior sent messages=3, common prefix=2
```

这是本地消息投影复现，不是服务商命中率或费用复现。更早的相同前缀仍可能被复用，不能说“所有缓存必然清零”。不同服务商的写入断点/公共前缀识别会影响损失程度。

**测试缺口：** `src/plugins/model.rs:1278` 的 `context_references_preserve_the_raw_prefix_across_user_turns` 检查用户原文和 raw prefix 不变，并没有比较“上一次实际送出的完整投影”与下一次投影，因此它通过不等于缓存契约成立。

**建议：** 先明确投影稳定性语义，不要仅把资料从用户消息挪到尾部就宣布修复。

- 较完整的路线是：为已接纳的参考快照固定任务边界/版本，并以宿主参考事件或可重放派生状态记录，后续只追加，不重写已送出的历史；旧参考随合法检查点一起压缩。
- 必须覆盖重开、撤销、分支、参考内容变更和原始用户消息不被污染。
- 若刻意采用易变尾部，则需要按目标 provider 在易变内容之前写入稳定前缀断点，并验证 thinking/签名重放语义；这不是所有协议通用、也不是完整 append-only 的替代证明。
- 不建议把动态资料搬到 system 最前面，或停用插件掩盖问题。

### F2 — 高优先级：插件后的最终请求不在预算校准和 trace 的同一视图内

**证据链：**

- `src/agent.rs:1762` 在 `complete_with_activity` 前捕获 `budget_view`。
- `src/plugins/model.rs:969–1048` 随后执行模型 Hook、参考检索与注入。
- 注入成功时 `usage_matches_projection=false`（`:1046`）。
- Agent `src/agent.rs:1997` 因此不使用该次服务端 input 校准原先预算。
- `src/cache_trace.rs:170` 如实标为 `provider_budget`，不是最终出站请求。

停止复用错误测量是**正确的安全行为**，不是建议删除的保护。但是，启用参考资料的常见路径会持续退回粗估，最终参考位置的变化又不在旧 trace 中。这使“精确校准”和“缓存定位”在插件场景下失效或退化。

**影响边界：** 可能使某些任务更早进入保守压缩/准入检查；本次未量化提前多少。不能把一次 trace 的 append_only 当作真实 wire 不变的证明。

**建议：** 先复用现有接口建立统一的最终投影身份：消息、工具、有效配置、参考版本。在最终转换/发送边界补内容无关指纹，并与实际 usage 关联。外部模型插件应有独立的观测边界，不能把内置 HTTP 指纹当成所有出口。

### F3 — 中高优先级：当前用量结构不足以优化真实缓存写入成本

**证据：**

- `src/model.rs:49` 的 Usage 有 input/output/cached/reasoning/web_searches，但无 cache write 字段。
- `src/provider/anthropic.rs:253–276` 确实读取 created/read/uncached，并将三者正确合并为 total input；后续输出的公共 Usage 只保留 total input 和 cached read，创建量及 TTL 细分丢失。
- `src/provider.rs:525` 的通用读取也未保留 `input_tokens_details.cache_write_tokens`。

这不是“缓存输入被重复加总”的错误；当前输入总量语义是合理的。问题是把 `input-cached` 全当普通未缓存输入，会混合收费不同的普通输入与缓存写入，无法可靠比较压缩策略的实际费用。

当前官方文档也不能继续概括成“所有 OpenAI 缓存都只有读折扣、没有写入费”：新旧模型的写入/断点/寿命语义不同。必须按模型、端点和实际报告字段处理，不能从代理模型名直接推定。

**建议：** 扩展现有 Usage 的可选字段，保留 cache write 与可获得的 TTL 分项、原始用量覆盖率；继续确保其为总 input 的组成部分而不是额外重复计数。未知价格或未知字段应显示未知，而不是推导免费。不必先建设新的统计平台。

### F4 — 中优先级：带原生搜索时，检查点不再保持完整工具前缀

**源码确认，未增加该场景的端到端 mock：**

- 主请求 `src/provider.rs:1387` 将 Responses 原生工具附加到 definitions；Anthropic 在 `:1419` 做类似附加。
- `checkpoint_payload` 的 Responses 分支在 `:2155` 传空原生工具列表；Anthropic 分支同样没有附加主请求的原生搜索定义。
- 主请求还会过滤同名本地 `web_search` 定义（`:1327`），检查点没有完全相同的过滤流程。

不让摘要再次付费搜索是合理目标，但**移除工具定义不等于仅在尾部追加摘要指令**。工具是缓存前缀的一部分，主请求与检查点因此可能不能共享期望的工具前缀。

`checkpoint_payload_preserves_the_cached_prefix_and_appends_one_instruction` 当前主要验证 Chat/DeepSeek 的函数工具场景（`:2864`），不能证明原生搜索路径。

**建议：** 增加 Responses/Anthropic + native search + 同名本地工具的 payload 对比。按协议评估“保留定义、禁止本次调用”的能力及缓存影响；如当前协议无法同时满足，则明确记录该模式检查点可能冷缓存，不要无证据承诺复用。不要机械地向所有端点添加 tool_choice 参数。

### F5 — 优化机会：provider-specific TTL、断点和路由策略不完整

- Anthropic `src/provider/anthropic.rs:165` 的顶层 automatic caching 是当前官方支持的推荐入口，不能误判成非法字段。当前没有显式稳定前缀断点或 1h TTL 配置。
- 官方文档说明自动模式仍有 20-position lookback；当前文档对连续 tool_use/tool_result 有合并计数规则，因此不能简单把“并行 20 个工具”说成必定越界。
- 默认 5m TTL 从写/读请求开始算起，长模型生成和长工具等待都消耗该时间。是否值得 1h 应由请求间隔与写入溢价决定，不能全局强开。
- Responses 当前没有 prompt_cache_key、模型适配的 lifetime 或 breakpoint 配置。但 key 不保证命中；当前官方文档还说明新旧模型对 key 的用途不同，不应把“缺 key”当成已确认根因。
- DeepSeek 默认缓存，但当前文档强调已有完整 prefix unit、公共前缀识别、构建延迟与 best-effort；有公共文本不等于本次必然命中。

**建议：** 能力检测/明确用户配置优先，默认保持简单。只在证据表明 TTL、断点或路由是瓶颈时增加对应策略，不增加无用户收益的定时保活/付费预热。

### F6 — 优化机会：MCP/插件大文本不像 Shell 那样有统一的常规可恢复投影

`src/mcp.rs:230–259` 在图片归档后把整个结果对象序列化为 ToolResult 字符串。传输层 8 MiB 限制是安全上限，不是 token 成本目标；`content` 与 `structuredContent` 也可能重复表达同一结果。并非所有重复都可以直接删除。

Shell 已有每流 64 KiB/2000 行门槛、可恢复路径和诊断预览（`src/shell.rs:23–27`、`:521`），不能再把它描述成完全无输出管理。通用旧工具结果预览则主要是 hard-limit 兜底（`src/context.rs:850`），不是日常优化。

**建议：** 先用真实样本区分必须完整的证据、重复序列化与确实超长文本；优先在结果首次进入模型时形成稳定的 artifact+状态/错误/定位预览，复用归档和 history 工具。不要每过一轮就追溯改写旧结果，避免破坏缓存。归档失败不得让已执行的外部操作被重跑。是否推广由任务质量和最终费用决定。

### F7 — 策略局限：固定 90% 压缩是容量策略，不是所有任务的成本最优解

`src/context.rs:347–359` 以窗口 90% 和安全余量计算阈值，摘要后保留最近约 32k。这个策略简单、可解释、能避免频繁失去缓存；本次不将它列为 bug。

但它不看输入/读取/写入/输出价格、未来任务轮数、缓存寿命、上下文噪声或摘要导致的回读。因此不能证明跨模型、跨任务最便宜。

一个可比较的判据是：

```text
未来请求节省的费用
  > 摘要输入与输出费用
    + 改写前缀后的冷启动/重新写入费用
    + 额外回读/修复费用
```

在每项实际计费口径已知且互斥时：

```text
总费用 = 未缓存输入 × 单价
       + 缓存读取 × 读取价
       + 各 TTL 缓存写入 × 对应写入价
       + 输出 × 输出价
       + 付费工具与辅助调用费用
```

示意：若读取价格为普通输入的 0.1 倍，100k 已缓存输入的输入费用可能低于 20k 冷输入。因此“压到原来五分之一”不是费用降低五分之一的证据。这只是算术示例，不是 Kroma 的实测收益。

**建议：** 先把当前策略作为 baseline。只有同任务对比证明有收益，再提供可选的 provider/workload-aware 策略；不先引入复杂的自动经济决策系统。

### F8 — 证据局限：不能用现有历史实验支持“当前最优”

`benchmarks/README.md:3–17` 明确说明旧实验原始记录在仓库之外、部分不可从 clone 重算、历史代码与当前实现可能不同。这是诚实披露，不是缺陷；但也意味着这些数字不能证明当前版本优于所有竞品。

Token 估算器（`src/token_estimate.rs:8–27`）来自 43 个实测 delta 的保守拟合，保留服务端校准是合理的。它不是精确 tokenizer，也不能凭这些样本保证所有模型、语言、emoji、opaque reasoning 和图片都不低估。优先补充目标模型的边界样本，不以“估算偏大”直接取消容量保护。

## 4. 推荐实施顺序

### 第一阶段：修具体契约，不换架构

1. 增加以“前次实际发送投影”为基准的回归：同任务多个工具轮、下一用户任务、参考内容更新、重开/撤销/分支。
2. 修 F1，明确参考快照生命周期；保持原始用户内容和工具配对不变量。
3. 让最终投影身份、测量与内容无关 trace 对齐。补 effective model/protocol/config、native tools、请求开始/结束和可获得的 provider request id；不记录正文和密钥。
4. 给 native-search 检查点增加跨协议 payload 契约测试。

### 第二阶段：补齐真实成本信息

在现有统计中增加可选 cache write/TTL 分项、重试/检查点等调用分类和未知覆盖率。任务级总成本包含额外回读和辅助调用；不能只看最后一条前台命中率。

### 第三阶段：小规模同任务验证

至少覆盖：无插件长工具循环、带参考插件、多用户任务、长等待、native search、超长 MCP 文本、会话重开。

对照条件保持同端点、同模型、相同推理设置和任务输入；隔离或记录两组互相预热，交错顺序、多次重复。先验收质量和必要验证，再比较请求数、input/output/read/write、完整费用及任务延迟。真实 provider 测试可能收费，应另行明确后运行。

只有这些数据支持，再决定 TTL、输出投影门槛或压缩阈值调整。**不优先做语义答案缓存、每轮摘要、任意清除旧结果、强制降低用户推理等级或全局强加缓存字段。**
