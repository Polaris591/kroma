# Kroma Rust 编码任务：过度定位与模型轮次研究

日期：2026-11-10；状态：**探索性消融及反向顺序检验完成，尚未批准生产默认变更**。

## 目标与不可降低的验收标准

同一模型、同一端点、同一思考等级下，在**完整正确、按要求运行验证**的前提下，减少复杂 Rust 任务的无效检查次数、模型请求、总耗时和实际 Token 成本。不同阶段的显著差异应优先解释为可测现象，不把局部样本当成“理论最优”。

- Kroma：合并后 Windows Release `kroma 0.4.0 (ce0b38641eb1)`。
- 对照 Pi：1.5.0，使用相同 `deepseek-v4.1-flash` / High / Cobblemon Chat Completions 端点和相同凭据。
- 用户侧可选插件均关闭；任务项目和 WAL 隔离；独立测试验收。
- 所有日志与结果留在 Windows `D:/Kroma/experiments/`；本报告不包含任何凭据。
- 实验脚本：`benchmarks/round6_rust_trace_diagnosis.py`、`benchmarks/round6_rust_guidance_ablation.py`。

## 1. 三轮已有 Rust WAL 轨迹的关键归因

来源：`D:/Kroma/experiments/kroma-round5-complex-session-fixed/`，首轮 Pi 来自 `D:/Kroma/experiments/kroma-round5-complex-current/`。

| 指标，三轮顺序 | Kroma | Pi 1.5.0 |
|---|---|---|
| 180s 内通过 | 1/3 | 2/3 |
| 已完成模型响应轮数 | 16 / 14 / 18 | 11 / 10 / 10 |
| **首次修改之前的检查操作** | **15 / 19 / 17** | **8 / 11 / 10** |
| Cargo 测试耗时 | 63 / 65 / 78 秒 | 72 / 83 / 54 秒 |
| 总普通检查命令耗时 | 2.4 / 3.9 / 2.2 秒 | 约 0.7 / 0.9 / 2.1 秒 |

检查次数的 Pi 统计**包含其原生 `read` 工具**；不能只计算 Bash `grep/sed` 而漏掉原生读取。完全相同的源码检查指令很少被重复；Kroma 更多是连续读取多个不同的窄切片。

**结论：** Kroma 的源码检查本身是毫秒级，不是主要本地开销。重要的问题是模型多次反复决策、延后形成可修改的证据闭环。首轮完成的 Kroma 任务耗时约 140.2 秒，其中 `model_ms=74.6s`，`tool_ms=65.5s`，工具时间主要是 Cargo 编译测试（约 63s）。更快的执行路径必须同时减少无效模型轮次并正确识别 Cargo 编译的冷启动成本。

局部测试耗时差异很大、实验含有 180 秒截尾；**不应**根据单次完成/超时归因 Rust Agent 本身的全部性能损失。Pi 也会出现编译较慢或超时。

## 2. 对现有提示词的源码检查

`src/prompt.rs` 的 `EXECUTION_GUIDANCE` **已经明确要求**聚焦搜索、找到证据后修改、完成验证后停止。再追加“不要重复调用工具”并不能解释已经观察到的几十次不同文件切片读取。当前没有证据证明需要增设专用搜索工具、Planner 或并发调度。

## 3. 同一 Kroma 的单变量指导消融

保持 **同一个已发布二进制、模型、High、端点、四个内置工具、任务夹具、关闭可选插件** 不变。唯一变化：在任务消息末尾追加一段约束执行顺序的通用指导：

> 首轮组合定位失败测试和实现代码；证据足够后优先进行最小修改；只有确实需要复现才能先做昂贵 Cargo 测试；修改后先运行用户指定的定向测试；失败后继续诊断，不省略必要验证。

这只是 **benchmark-only 用户消息增强**，**不是**替换系统 Prompt，也没有改生产 Agent Loop。

初次数据：`D:/Kroma/experiments/kroma-round6-rust-guidance/results.json`。任务与文件目录独立。**复核发现：首次 WAL 三组由于每组分次重启脚本，原随机顺序被重复初始化为「原版先、指导后」。后一臂可能占到 Cargo 预热的便宜，故前三组只作探索性观察，不作为严格因果对照。** 已修正脚本为由任务名和重复编号决定稳定顺序，并在全新的目录进行反向顺序试验。

### 复杂 Rust WAL：3 组早期配对（基线总是先运行，存在顺序偏差）

| 第几轮 | 原版 | 聚焦指导 |
|---|---|---|
| 1 | 超时 180.5s | **通过 149.6s** |
| 2 | 超时 180.1s | **通过 139.1s** |
| 3 | **通过 132.7s** | 超时 180.1s |
| 180 秒完成率 | 1/3 | **2/3** |
| 修改前的源码检查次数 | 18 / 13 / 14 | **10 / 10 / 9** |
| 合计工具调用（含超时前调用） | 61 | **45** |

这三组观察中，修改前的检查次数平均从 15.0 降到 9.7，约减少 **36%**，工具调用从 61 降到 45，约减少 26%。两组通过的指导任务均运行了 Cargo 测试。**这属于行为迹象，不是已经排除运行顺序和 Cargo 缓存的因果结果。**

**重要反例：** 第三次指导组虽然在第 10 个工具就完成修改、前期检查只有 9 次，但在 Cargo 编译之后第 10 次模型请求悬挂约 60 秒直到实验超时。因此“减少无效搜索”不能保证端到端成功，也不应把这一次失败直接归咎于定位策略。需要分开衡量网关长尾等待。

### 反向顺序检验：聚焦指导先运行（新实验目录）

完整结果：`D:/Kroma/experiments/kroma-round6-rust-balanced/results.json`。新版驱动按 `SHA256(seed, task, repeat)` 固定交叉顺序，因此即使分两次执行，也不会重置为同一臂先跑。

|---|---:|---:|
| 外部回归验收 | **通过** | 通过 |
| 墙钟耗时 | **113.1s** | 140.9s |

指导组这次**先运行**，仍以更少前期检查、更少模型/工具请求完成任务。它削弱了“效果完全来自后运行的 Cargo 缓存优势”的反证，但单次反向实验不足以排除模型/网关随机波动；也不能将这一结论推广到其他 Rust 任务。

|---|---:|---:|

## 4. 对结果的反证与边界

1. **单个复杂任务反复测试，不等于跨任务泛化。** 当前改善主要出现在 Rust WAL 恢复这一种任务；不能自动推广到所有 Rust 开发。
2. **追加在用户消息末尾，不等于生产环境系统提示词。** 指导的角色、位置、长度和措辞都可能改变行为；不能把它的成功直接当作系统默认 Prompt 修改后的收益。
3. **系统模型/网关长尾与 Cargo 冷编译属于外因/中间环节。** 两者必须按阶段独立统计；出现截尾时不能用普通平均数声称稳定提速。前三组 WAL 还存在「基线先、聚焦后」的顺序偏差，已经在反向顺序实验中检查，但尚未做完全平衡的重复试验。
4. **更早编辑的反向风险：** 在证据不足时盲改、漏掉隐性约束、跳过用户要求的验证。因此指导必须保留“证据充分”和“按需扩大验证”条件，而不能僵化限制读取次数或禁止失败复现。
5. **Kroma 原系统提示词已有相近规则。** 一味加长全局 Prompt 可能增加每轮输入成本，并在小任务上适得其反。

## 5. 决策与下一步

**判断：定位策略存在跨顺序的可复现优化信号，但跨任务泛化与默认生产改动的证据仍不足。**

- 保留当前 Shell + edit_file、Agent Loop、上下文压缩和默认 Prompt。
- **P1 · 已观察：** Kroma 在复杂 Rust 问题中首次编辑前检查和模型回合过多，导致 180 秒内完成率不稳定；优先针对决策收敛进行测试。
- **P2 · 已观察：** 单独加长指导可能增加小任务请求和耗时，不能把复杂任务的提升无条件推广。
- **P2 · 已观察：** 测试框架不应把“代码能通过外部验收但代理没有运行用户要求的测试”标成无条件完成；分开记代码正确、流程遵守、任务是否收尾。
- **下一种最小实验：** 只将现有系统 `EXECUTION_GUIDANCE` **替换为更短更明确的一段**（而非追加提示），制作隔离实验二进制；加入一个不同类型的复杂 Rust 修复作为留出题，至少和小型 Rust 一起做交叉重复。成功率与任务验证不下降，才考虑产品默认变更。
- 另单独查看超过 60 秒的模型请求长尾和 Cargo 编译首次耗时；别把它们误判成 Shell Registry 分发问题。

**不建议：** 为此加入 Planner、验证器、按文件数量硬限制 Shell、默认工具并发或第二种上下文策略。
