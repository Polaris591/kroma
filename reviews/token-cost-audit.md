# Kroma Token 开销审查（第一轮）

## 范围与结论

本轮先审查实际发送给模型的内容，不修改运行机制，不新增预算、审批、次数限制或强制工作流。不通过关闭用户能力、丢弃原始证据或单纯折叠界面来降低表面数字。

需要分别看三个问题：下一次请求的上下文长度、整个任务累计的输入/输出用量、其中实际缓存命中的输入。它们不能直接等同于费用；本轮没有真实请求账单，不能给节省比例。

## 已确认的实现

- `src/shell.rs:23`、`src/shell.rs:521`：命令输出已有 64 KiB / 2000 行的内联阈值，超长内容保留文件，返回预览和诊断线索。因此不应重新实现一套 shell 日志归档。
- `src/mcp.rs:2570`、`src/mcp.rs:2599`：默认用两个入口按需发现，不是默认把所有远程工具定义全部注入；显式设置 `KROMA_MCP_EAGER` 时才切到提前注册路径。`src/app.rs:174` 调用这个选择入口，因此不能仅凭“MCP 全开”判断说明全部常驻。未读取用户实际环境，不能断言当前会话用了哪种模式。
- `src/context.rs:1153`、`src/context.rs:1553`：请求历史是原始记录的投影；未被摘要覆盖的消息仍进入后续请求。自动摘要主要在上下文接近容量时触发；通用工具结果缩短是超限兜底，不是常规成本优化。
- `src/context.rs:850`：只有达到硬阈值才尝试通用工具预览；保留原始会话及工具调用/结果配对。任何新策略都必须保留这些不变量。
- `src/agent.rs:1618`：一个任务内复用工具定义和额外占用计算，已经避免每轮重复构建。这是本地计算优化，不能当作已减少线上输入 Token。
- `desktop/src/components/ContextMeter.svelte:23`：界面已有系统提示、项目指令、扩展、工具、消息的占用分类。不应另造重复面板；目前“对话消息”未进一步区分用户消息、模型回答和工具结果。

## 首批优化候选（尚未实施；不是收益排名）

### 1. 工具结果：先解决明显的重复和无边界文本

`src/mcp.rs:230` 在媒体处理后将 MCP 响应整体序列化为工具文本；`src/tools.rs:21` 的结果内容也是一个字符串。目前这条返回路径没有 shell 同款的常规文本预览处理。应优先检查重复内容和超长文本，并用可恢复的方式提供模型需要的部分。

真实案例：本次浏览器测试返回结果时回显了完整驱动代码。本地三份合成驱动分别是 30,770、31,810、30,429 字节。这只是脚本文件大小，不是 Token 测量，也不等于一次线上请求的总长度。不能用直接删除某个 MCP 内容块的方式修复，因为块内可能包含唯一的结果或错误证据。

### 2. 历史复用：减少已过时的大结果，不破坏缓存和证据

普通请求目前会继续携带未摘要覆盖的工具输出。应先验证哪些输出已经被后续信息取代，以及按需回读的代价；不要把“模型看过一次”当作“以后一定不需要”。改变旧消息会影响稳定前缀，应同时比较缓存命中，避免字数变少但实际成本反而增加。

### 3. 测量：复用现有统计，建立可比较的任务样本

优先区分固定提示/工具说明、当轮工具结果、历史工具结果、模型回答，以及摘要/标题等额外调用。字节估算必须标明估算；实际 Token 和缓存数据以模型服务返回为准，未知值不能算作零。先比较同一任务的正确性、请求次数、输入、缓存和输出，再决定策略是否值得保留。

## 保护要求

- 完整输出可回查，错误、退出码及执行结果不被改写。
- 不因归档失败重跑已经发生的外部操作。
- 不更改 WAL 原始证据，不拆散工具调用及结果。
- 不为了省 Token 减少必要验证，不强制更换用户模型。
- 先复用已有归档、历史读取、上下文报告和缓存机制，不先搭建复杂“智能压缩系统”。

## 批判性复审：先处理缓存失稳，不先做全局截断

前一版把“工具输出”排在“测量”之前，证据不足。输出很长不自动代表无用；减少请求字数也不自动代表降低实际开销。压缩调用、额外回读和缓存损失都可能抵消收益。源码里的超限保护不能仅因触发较晚就被认定为性能缺陷。

### 已离线复现：插件补充内容会改写上一轮已发送的用户消息

- `src/plugins/model.rs:637` 的 `with_packs` 只给最新一条真实用户消息附加补充内容，不写入原始历史。
- `src/plugins/model.rs:1019` 在下一次请求中重新从原始历史构造投影；`src/plugins/model.rs:1119` 将该投影交给下层模型。
- 因此有上下文插件时：上一轮送出 `用户 A + 补充资料`；用户 B 到来后再送出历史，旧用户 A 变回 `用户 A`，补充资料仅附在 B 上。即使补充资料完全相同、没有改系统提示和工具，上一条已发送的消息也变了。更早的前缀未必全部失效，不能称为“整个缓存必然清零”。
- 临时 Rust 单元断言已实际验证：同一任务内追加模型消息时原用户内容不变；新增用户消息后，“旧用户内容仍等于上次发送值”的断言失败。测试直接调用实际 `with_packs`，未访问外网或真实模型。临时探针已移除，生产逻辑未改；本次没有把失败用例作为修复后通过来报告。
- 这是已确认的本地请求前缀不稳定路径，足以列为优先修复对象；仍不能证明用户这次掉缓存全部由它导致，后者需要关联实际失效请求及服务返回的用量。

### 已确认的诊断盲区

`src/agent.rs:1762` 在插件改写前捕获预算投影；`src/cache_trace.rs:170` 明确标为 `provider_budget`。而插件补充和请求 Hook 在 `PluginModelHooks::projection` 内发生。因此旧 trace 即使显示仅追加，也不能排除实际送出内容发生了上述变化。`src/provider.rs:2204` 才构造内置 HTTP 模型的请求体；外部模型插件还有自己的发送边界，不能把某一处指纹当成所有宿主的完整链路证据。

### 调整后的顺序

1. 优先解决已复现的历史投影不稳定，并明确需要维持的跨用户消息、跨重开会话和插件内容更新语义。不能简单把动态资料搬到最前面的系统提示，也不能靠停用插件掩盖问题。
2. 复用已有用量统计和无正文指纹，核对失效发生在哪次请求、变化在什么位置；不先搭建新的统计平台，不记录密钥或完整敏感提示。
3. 用同一任务比较完成质量、额外调用/回读、输入输出和实际缓存数据，再决定是否扩展通用长输出处理。没有实际收益时停止扩展，不重写压缩系统。

审查本身也有成本：先聚焦一个已复现问题，不用“省 Token”作为无边界读文件、重复审查或额外分派任务的理由。
