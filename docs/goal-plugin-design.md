# Goal 插件完整设计方案

状态：已实现（2026-11-08 起），发布前验证未完成。插件 `examples/plugins/goal` 提供 Goal 规则与
`goal_checkpoint` 工具，宿主控制器 `src/task_control.rs` 负责执行、持久化与停止，CLI/JSONL、
TUI 与 Desktop 均可启动目标、查看状态、暂停、恢复和取消。`tests/task_control_e2e.rs` 的 22 个
端到端用例覆盖提前收尾拒绝、受阻暂停、崩溃与重复重启、插件回复畸形/超时、用户停止与显式取消、
伪造证据、伪造元数据、长会话、分叉与新一代历史以及投影完整性等路径。安装与使用见
[examples/plugins/goal/README.md](../examples/plugins/goal/README.md)。
仍待完成的是发布验证：真实 provider 上的完整任务闭环、人工部署演练与恢复保证的实测；
本文其余部分按目标契约阅读，接口细节以源码与测试为准。

本稿取代 R0 的“原生 Goal capability + 独立 sidecar”方案，纳入批判性审查结论。

## 1. 产品定义

**给 Kroma 一个目标，让它自主执行、检查并交付；完成就结束，确实受阻就带着进度暂停。**

Goal 解决普通对话容易过早收尾、长任务目标易丢失的问题，不是无限续跑器，也不是另一套 Agent。
用户不需要写工作流、选角色、管理任务树或反复发送“继续”。

第一版必须做好六件事：目标保留、自动推进、事实可追溯、及时停止、中断可恢复、操作简单。
其中“事实可追溯”不等于证明任意自然语言目标正确完成。

### 1.1 设计原则

1. 一个会话至多一个当前目标，一个正常 Agent 执行循环。
2. 复用工具、压缩、取消、会话锁与 WAL；不另建调度器、数据库和后台进程。
3. 正常默认就能工作；高级行为由插件设置控制，不塞进模型参数。
4. 机器只核实能核实的事实；语义判断、未验证部分必须如实展示。
5. 用户新指令与中止优先；插件不能增加授权或自动重放未知副作用。
6. 新增机制必须通过对照实验证明收益，不能只凭演示或代码行数宣称更好。

### 1.2 不做的事

不做 DAG、多目标并行、定时任务、常驻 daemon、代理委员会、向量库、第二套压缩、自动 worktree/merge、
专用任务中心和默认收费的独立裁判模型。Goal 不依赖子代理、记忆或联网插件才能运行。

## 2. 用户体验与操作契约

```text
/goal 修复登录失败，补上回归测试，并通过相关检查
/goal                         # 查看当前目标与进展
/goal pause                   # 暂停，不回滚修改
/goal resume                  # 核对现场后继续
/goal resume 先只支持邮箱登录   # 追加用户修订后继续
/goal cancel                  # 放弃当前目标，不删除已做的工作
```

- 创建目标后直接执行，不再要求单独说“开始”，也不要求先填验收表。
- 验收点、检查命令与证据都是可选的记录手段；不强制数量，也不限制条数。
- 自行查项目说明、测试入口和既有实现；可自行查证的事情不反复问用户。
- 真正缺少授权、凭据、外部条件或关键需求时暂停，明确所需信息和继续方式。
- 运行中可用现有停止按钮/Ctrl+C；`/goal pause` 走相同取消路径，不等待插件回调批准。
- 当前目标正在运行时，不允许 `/goal <新目标>` 静默覆盖；先停止当前执行。
- 当前目标已暂停或结束时，显式 `/goal <新目标>` 可开始新目标，旧记录保留在会话历史中。
  `/goal resume` 只恢复当前目标，不增加多目标历史管理界面。
- 暂停后的普通输入仍是普通聊天，不猜测它是否在回答旧目标的问题，也不自动复活旧目标。
  回答阻塞问题可直接用 `/goal resume <补充内容>`。
- 运行中的普通 steering 仍属于当前任务；按第 8 节修订要求，不要求用户掌握新语法。
- 状态展示目标、进展、已执行检查、模型判断、未验证项和暂停原因，不显示虚假的完成百分比。

空正文、未知子命令、无目标时 resume 都给出明确用法，不隐式创建新目标；
已完成或已取消的目标只在用户显式 resume 时重新打开，永不自动复活。
旧 Goal 的继续必须由用户显式重新发起目标或通过已有会话分支能力处理。

## 3. 架构决定：真实插件，宿主保留执行权

### 3.1 最终选择

采用 **Node 进程插件 + 一个窄的 `task_control` 宿主能力**。

- 插件拥有 Goal 的命令解析、验收点校验、检查计划、结束规则与提示约束。
- 宿主拥有唯一执行循环、消息提交、控制状态、输入边界和取消。
- 新能力允许插件提出“启动本轮任务、更新控制状态、正常结束前继续/结束/暂停”的建议。
- 只允许一个活动控制器，不提供控制器链、嵌套策略或任意 Agent 内部对象访问。
- 插件没有自己的权威 Goal 文件，也不启动 Kroma 子进程执行目标。

这是一个有限协议扩展，不是通用工作流平台，也不是将整项功能写进宿主后用清单充当开关。

### 3.2 路线比较与代价

| 路线 | 优点 | 主要问题 | 决定 |
| --- | --- | --- | --- |
| shell 外层循环 | 演示代码短 | 不同任务边界、取消/恢复割裂，容易重复执行 | 不采用 |
| 纯现有进程插件 | 不改宿主 | 事件不能阻止结束，现有 slash 回复只能输出文本 | 无法满足契约 |
| 原生 Goal + 声明式清单 | 少一次进程调用 | Goal 业务进入核心，形成专属 capability 和全宿主耦合 | 不作为首选 |
| 进程插件 + 窄任务控制 | 业务独立，关键边界由宿主保证 | 需要新增协议和适配，仍有明确维护成本 | 采用并先做最小原型 |

不声称最后一条已被证明代码最少。原型阶段必须记录改动文件、接口和测试负担；
若控制接口开始扩展为调度器或普遍侵入模型/provider，停止扩展并重新评审，而不是强行实现此稿。

### 3.3 职责表

| 责任 | 插件 | 宿主 |
| --- | --- | --- |
| 理解目标、形成验收点 | 通过当前模型与检查点完成 | 提供原始用户输入与修订来源 |
| 校验 Goal 数据结构与结束规则 | 是，无额外模型请求 | 对控制边界、事实与所有权再次校验 |
| 选择并执行项目工具 | 提示当前 Agent 自主选择 | 既有 ToolRegistry 执行，不由插件另开 shell |
| 状态 | 只接收快照、提出更新 | 唯一权威，持久化后才生效 |
| 用户输入与取消 | 无否决权 | 唯一决定者 |
| 历史、压缩与恢复 | 不直接读写 WAL | 复用现有会话设施 |

## 4. 与现有 Kroma 的差异

当前 [Agent](../src/agent.rs) 在没有工具调用且没有待处理 steering 时正常结束。
[插件命令适配](../src/plugins.rs) 将外部回复转成文本；事件与 `task_finished` 是异步、尽力投递的通知，
不能成为可靠的控制或状态提交机制。见[插件指南](../examples/plugins/README.md)。

需要新增的宿主能力只有以下边界，不新增另一套执行器：

1. 显式用户命令可返回一个准备好的任务，由宿主启动一次正常 Agent 运行。
2. 控制器工具可提出小型状态更新，与本次工具结果一并提交。
3. 模型准备正常结束时，同步询问控制器；错误、取消不经过此回调。
4. 宿主在正常执行路径计数、维护检查事实，并在既有 WAL 消息上保存控制快照。

CLI/TUI/Desktop 必须接入同一分发结果。不能把 Desktop 输入 `/goal` 当普通文本直接发给模型。
普通输入、现有命令、follow-up 队列和公开 `Agent::run` 行为保持不变。

## 5. Manifest、版本与加载

以下为拟议清单；当前版本会拒绝未知 capability，不能提前部署。

```toml
api_version = 2
id = "goal"
name = "Goal"
version = "0.1.0"
command = "node"
args = ["main.js"]
capabilities = ["task_control"]
prompt = """
仅在宿主提供活动目标时使用 Goal 规则；普通任务不自行建立目标。
先理解和执行目标，在最终检查前登记计划，检查之后不要执行无关工具。
准备收尾时调用 goal_checkpoint；真实受阻就说明原因，不用完成短语代替证据。
用户新指令和停止优先；区分已执行检查、模型判断与未验证部分。
"""

[settings]
# 没有请求/时间预算，也没有拒绝次数上限；用户停止才是硬边界。

[[commands]]
name = "/goal"
description = "启动、查看、暂停、继续或取消当前目标"

[[tools]]
name = "goal_checkpoint"
description = "记录当前目标的验收、进展和完成或阻塞声明；不能扩大权限"
invalidates_context = true
# parameters 使用第 9 节的字段契约；此处省略重复 JSON Schema。
```

- `task_control` 仍须 API 2 和进程 command；不引入无需 executable 的专属原生能力。
  Goal 运行代码只使用 Node 标准库，首版不引入 npm 依赖或单独的 Schema 引擎。
- 所有旧 V1/V2 插件保持原帧与原行为；仅新能力请求增加控制字段和回调。
- 同一运行时最多一个启用的 `task_control` 提供者；冲突在启动/idle reload 时明确报错，不按顺序叠加。
- 该能力首版只允许一个控制命令。宿主根据其声明名称保留无附加参数的 `<命令> pause` 与 `<命令> cancel`，
  直接执行用户暂停/取消，不等进程回复；其余子命令由插件解释。宿主不硬编码 goal 插件 ID 或验收业务。
- 启用不代表立即创建目标。没有活动目标时不调用结束回调，也不加载 Goal 动态上下文。
- 模型是否看到插件静态工具/提示，沿用当前插件贡献机制，不为隐藏它们再增加作用域框架。
  这部分 token 开销必须计入对照实验，不能宣称启用插件也绝对零成本。
- 普通任务禁用插件时，无 Goal IPC、控制快照和额外模型请求。
- 活动任务中不允许 reload；暂停后代码变化由插件自行校验数据兼容性，不偷偷迁移或自动重启。
  插件的发版号不阻止用户继续自己的目标。

## 6. 权威状态与最小数据模型

### 6.1 宿主管理字段

| 字段 | 含义 |
| --- | --- |
| `version`、`owner` | 控制记录版本与所属插件 ID |
| `id` | 宿主生成的目标 ID，模型/插件不得冒充既有目标 |
| `revision` | 用户要求修订号；仅宿主因真实用户输入而推进 |
| `seq` | 已接受的控制状态更新序号，用于拒绝过期插件回复 |
| `scope` | 当前 archive 的身份摘要与会话 history generation，不是模型传入路径 |
| `status`、`reason` | 四种目标状态与原因码 |
| `run_id`、`usage` | 当前执行段标识、次数、时间和跨段已知累计值 |
| `checks` | 插件登记的通用命令检查契约；宿主只验证执行事实，不解释 Goal 业务条件 |
| `verification_epoch`、`checkpoint_basis` | 当前检查轮次，以及最近检查点绑定的 revision/轮次 |
| `data` | 插件 Goal 数据：验收点、进展、声明与证据引用 |

`seq` 只随控制状态更新推进。普通请求计数和检查结果记账不改变用于工具并发校验的 `seq`，
避免模型刚生成检查点、宿主因记录该模型响应便使它永远过期。
最新消息位置决定快照先后，不依赖时间戳或 JSON 文件 mtime。

### 6.2 插件数据

原始目标和每次用户修订都以已有 user 消息为准；Goal 数据保存对应消息位置和紧凑摘要，
不以模型重写的摘要替换原始授权。

- `criteria`：稳定 ID、要求文本、来源 `user`/`derived`、来源引用、判断、相关检查/证据和说明。
- 检查计划由工具输入交给插件，再通过 control.checks 登记到宿主字段；data 中不再保存另一份计划。
- `summary`、`next_step`：最近进展与下一步。
- `claim`：`working`、`done` 或 `blocked`；只是模型声明，不是目标终态。
- `block_reason`、`unverified`：受阻原因与未验证项。

每个被接受的控制检查点由宿主写入 checkpoint_basis，绑定当时的 revision 与 verification_epoch。
普通工具导致轮次变化后，旧 done 字样仍可保留为历史，但其声明依据已失效，不能放行。
宿主不解析 data.claim 判断业务完成；它校验检查点依据和通用检查契约，插件判断 Goal 声明与验收项。

唯一的容量边界是单条控制记录的传输大小（256 KiB），用于防止畸形数据撑爆 IPC；
它不限制任务规模、验收点数量或检查条数。投影必须保留用户原文与全部当前条件，
不允许为省 token 静默截断。

## 7. 状态与前台任务是两件事

Goal 对外只有 `running`、`paused`、`completed`、`cancelled`。没有记录表示没有目标。

| 当前状态 | 事件 | 新状态 |
| --- | --- | --- |
| 无当前目标/旧目标已结束或暂停 | 显式 `/goal <正文>` | 新 ID，running；旧记录保留 |
| running | 有效检查点 | running |
| running | 有效正常结束 | completed |
| running | 受阻、中止、插件故障 | paused，带原因 |
| paused | 显式 resume | 同 ID，新执行段；有补充输入则修订号增加 |
| running/paused | 显式 cancel | cancelled |
| completed/cancelled | 显式 resume | 同 ID 重新打开；绝不暗中执行 |

**`TaskFinished.status` 继续表示前台本轮完成/失败/取消，不表示 Goal 完成。**

| 前台情况 | 既有前台状态 | Goal 状态 |
| --- | --- | --- |
| 交付完成 | completed | completed |
| 有序地报告受阻/执行上限 | completed | paused |
| 用户 Ctrl+C / 停止按钮 | cancelled | paused |
| 显式运行中 cancel | cancelled | cancelled |
| provider 或工具基础设施故障使任务失败 | failed | paused |
| 普通聊天 | 原语义 | 不改变已暂停 Goal |

新增通用 `TaskControlChanged` 事件/快照字段，包含 owner、ID、revision、status、reason 与有界进展摘要；只能在 WAL 提交后发出。
界面必须结合它显示“目标已暂停”，不能看到前台 completed 就写“目标已完成”。
JSONL 保留旧事件，新增可忽略的控制事件；事件只是展示，恢复以 WAL 为准。

## 8. 用户改口、steering 与权限

1. 目标运行中接收的真实 steering 在原有安全边界持久化；同一次提交提高 `revision`，使旧完成声明失效。
2. 新要求按正常用户指令顺序解释，后续明确修订可以覆盖先前要求。
   不把“原目标不可丢失”错误解释为用户自己也不能改变要求。
3. 插件收到修订来源，模型提交与新 revision 对应的检查点后才能再次完成。
   可以复用仍相关的工作，但旧 revision 的通过事实不能自动充当新要求的通过证明。
4. 模型不能提高 revision，也不能通过引用一段插件输出冒充用户修改了条件。
   `user` 来源须能匹配宿主提供的用户消息引用；文本匹配证明来源，不证明模型语义解释一定正确。
5. 新要求不会自动续跑；只有用户显式 resume 才授权下一执行段。
6. 切换话题、暂停、取消的用户要求优先；不让旧检查点强迫 Agent 继续之前的任务。
7. 开启 Goal 不扩大 shell、网络、部署、费用或文件权限。任务范围内的常规准备沿用现有授权，不新增反复确认。

## 9. 唯一模型工具：goal_checkpoint

必填字段：`summary`、`claim`。`revision` 缺省等于当前修订；其余字段按当前状态继承，全部可选。

| 字段 | 规则 |
| --- | --- |
| `criteria` | 可选的要求列表；省略表示继承，空数组表示清空。模型可随时修正自己的理解 |
| `checks` | 当前检查计划；变更必须显式提供完整列表，清除旧检查需解释 |
| `claim` | working/done/blocked；done 只是请求收尾，blocked 需明确原因 |
| `next_step` | 尚未完成时给出具体下一步，不用空泛“继续努力” |
| `block_reason`、`unverified` | 需要用户或无法验证的条件，原样进入最终报告 |

验收点判断为 pending/satisfied/blocked；证据使用已完成的调用 ID 或本轮最终交付引用。
证据 ID 由宿主核对当前目标与修订下的真实执行记录，查不到即拒绝该检查点，不会把假引用存进完成记录。
插件验证数据约束，宿主验证所有权、修订、原始执行事实与引用归属。
null 以及可选字符串的空占位符按未填处理；非空非法值、重复 ID、超限、错 revision 均拒绝。
空数组不是字符串占位符，须按以下显式删除规则处理。

### 9.1 嵌套字段契约

验收点字段固定如下；未知字段拒绝，不将任意扩展对象塞进控制状态：

| 字段 | 类型与约束 |
| --- | --- |
| `id` | 1–32 位字母、数字、下划线或短横线；当前列表内唯一，正常更新保持稳定 |
| `text` | 非空，至多 512 字符；不得只写“完成目标”替代具体条件 |
| `source` | user/derived |
| `source_ref` | user 时必填：`{message_index, quote}`；quote 为 1–500 字符的连续用户原文片段 |
| `kind` | command/deliverable/judgement |
| `assessment` | pending/satisfied/blocked |
| `check_ids` | command 时必须引用至少一项当前检查计划，不能使用不存在或重复的 ID |
| `evidence` | `{kind:"tool",call_id:"..."}` 或 `{kind:"final_answer"}` 的列表 |
| `notes` | satisfied 的 deliverable/judgement 项必须解释依据；不能因此标记为独立机器证明 |

插件对验收点 source_ref 使用宿主只读来源做校验；宿主对通用检查契约的 source_ref 做同等校验。
校验基于消息位置、角色和真实内容，只折叠空白后做连续匹配，不做语义猜测。
若提供来源引用，必须属于该目标原始输入或宿主记录的修订输入，不能引用工具/插件输出；不提供也合法。
final_answer 在检查点阶段只作为待交付引用；仅在实际最终候选被接受时兑现，不伪装成已完成工具。

检查计划条目为 `{id, command, source, source_ref?, rationale?}`：
ID 同上；command 非空且至多 2048 字符；source 仍为 user/derived。
来源引用可选：提供时必须是用户原文的连续片段；未提供时按模型选择的检查处理，执行事实仍由宿主核对。
原始用户命令不得仅凭 derived 的解释删除。比较执行命令时使用解码后的完整字符串及宿主工作目录，
不尝试理解命令内部的 cd、管道或复合子命令。

summary 至多 2048 字符，next_step/block_reason 各至多 1024 字符，unverified 至多 16 个非空短项；
总大小仍受控制数据上限限制。省略 criteria/checks 表示继承；显式空列表不是“未填”，必须按删除规则校验。
claim=blocked 必须有 block_reason；claim=working 必须有 next_step，首次建立时填写准备执行的计划。

### 9.2 调用示例

```json
{
  "revision": 1,
  "summary": "登录修复与回归测试已完成",
  "claim": "done",
  "criteria": [
    {"id":"C1","text":"登录恢复","source":"user",
     "source_ref":{"message_index":12,"quote":"修复登录失败"},
     "kind":"judgement","assessment":"satisfied",
     "evidence":[{"kind":"tool","call_id":"call-test"}],
     "notes":"功能判断来自回归用例；未验证生产环境"}
  ],
  "unverified": ["生产环境凭据与部署验证"]
}
```

示例继承已登记的检查计划；message_index 与 call_id 必须由本会话实际记录提供，不允许照抄示例值。
机器 JSON Schema 必须忠实实现以上字段、条件必填和大小约束，不再留待实现者自行定义完成语义。
模型参数中没有权限、真实退出码、目标 ID、`seq` 或完成状态写入权。

只在形成验收、重要进展、修订后对齐和准备结束时调用；不要求每一步写检查点。
正常模型工具循环不变；在一个 batch 里先声明 done 再执行其他工具，仍会因后续失效条件而不能直接完成。

## 10. 验收边界：事实与判断分开

### 10.1 三类输出，不做虚假的统一保证

- **已执行检查**：声明的命令真实执行、匹配当前计划、退出状态已知，并满足下面的新鲜度规则。
- **模型判断**：模型认为证据覆盖了业务/设计要求，必须给出依据，不标为宿主独立证明。
- **未验证部分**：环境缺失、外部条件、人工体验或无法机器判断的部分。

完成的含义是：当前必需条件有对应的完成判断，声明的有效检查通过，交付已保存，并披露未验证项。
不是“所有自然语言要求都被机器证明正确”。不增加 `verified_complete` 之类夸大保证的状态。

### 10.2 用户条件与模型补充条件

- 已登记为 user 来源的明确命令必须执行；用户要求的验证不能因缺环境就改写为“无需验证”。
  从自然语言提取是否遗漏命令仍是模型判断边界，须展示当前计划并纳入独立验收，不声称已经完全机器识别。
- 自然语言要求由当前模型转换成验收点和检查计划，不要求用户先批准每一项。
  这种转换本身属于模型判断，插件不能将它包装成独立验收。
- `user` 条件的删除/放宽需要对应的新用户修订；`derived` 检查允许因不适用而调整，但必须保留原因。
- 所有当前声明的检查都必须通过。不能把一个仍失败的检查留在计划里却声称检查全过。
- 替换模型选错的命令不必都找用户批准；原失败记录与替换解释保留在历史及收尾报告里，不能隐藏失败。
- 任务的必要条件无法验证时 paused；与用户目标无关的额外检查不得成为无限扩展任务的理由。
- 文档/研究/设计按真实交付、来源和用户约束评估，不强制运行无关代码测试。

不以“完成短语”、任意 exit 0、搜索成功或子代理退出 0 直接放行。
同一模型仍可能漏需求，因此真实完成率要由第 19 节的外部验收衡量，而不是由本插件自己的 completed 数量衡量。

## 11. 执行事实与新鲜度：采用可执行的保守规则

### 11.1 原始执行事实

控制器活动时，工具层在 after-tool hook 改写前保留最小执行记录：
调用 ID、实际执行参数、原始错误状态、shell 退出码（若有）、Goal ID/revision、检查轮次。
执行记录与对应 tool 消息同一次 WAL append 保存；没有结果或结果未知都不能算通过。

不把模型提供的退出码、经过结果改写后的文本或“未看到报错”当原始执行事实。
不建立第二个证据数据库，不复制完整日志；日志沿用现有 shell 归档路径。
没有原始执行记录的旧消息可用于人工/模型参考，但不能补造新协议下的机器通过事实。

### 11.2 检查计划与检查轮次

1. 检查命令可以执行后登记（补记已做的验证）。比较时精确匹配实际 shell 命令与工作目录，不解析 Bash/PowerShell 语法。
2. 宿主维护 `verification_epoch`。检查计划变更、用户修订、resume 和普通工具操作会开启新轮次。
3. 只有精确匹配当前登记命令的 shell 调用，才作为当前轮次检查；多条登记检查可依次执行而不互相失效。
4. 其他工具只会让“完成声明”失效，不会抹掉已经真实跑过的检查事实。是否需要重跑由模型判断，
   不为了保守而强制重复劳动；执行事实仍只认宿主记录。
   因此查看 diff、搜索或调用子代理应放在最终检查之前；不猜哪些 shell 是只读。
5. 进入新轮次后，已经被证明执行过的旧记录仍保留，但不能自动证明当前现场通过检查。
   需要重新检查时说明失效原因，不能把它记为普通的“为了更放心又测一次”。
6. 同轮次所有登记检查通过且没有后续失效操作时，机器检查条件才满足。
7. 插件检查点自身不改变工作区，不使有效检查失效；但修改其中的检查计划会使其失效。

这是刻意选择的保守规则，会有少量误失效，必须测量其重复检查成本；不同时承诺“完美判断所有写入”和“零重测”。
检查命令本身也可能产生副作用，多个检查可能互相影响；精确匹配不证明其语义可靠。
外部程序并发修改、恶意插件和恶意测试不在完整保证范围，不能为了消除这些边界造文件系统监控框架。

## 12. 结束决策与自动推进

`before_task_finish` 只在正常、无待执行工具的候选结束处调用。处理顺序固定：

1. 用户中止、待处理 steering 优先；有输入则先消费并提高 revision。
2. 宿主检查状态版本和执行事实；基础设施错误或失效引用不得放行完成。
3. 插件依据当前检查点返回 finish/continue/pause，不调用额外模型。
4. 插件要求当前 revision 有 done 声明、必要验收项非 pending/blocked；宿主另要求 checkpoint_basis 有效、
   当前登记检查全过且交付非空。语义判断仍按第 10 节披露；文本非空不证明语义正确。
5. 缺检查点、缺执行事实或条件未满足时，给出具体缺口和下一步，继续同一 Agent 循环。
6. 真正受阻返回 pause，并说明用户需要提供什么；不能以无限继续掩盖阻塞。
7. 回调之后再进行原子 inbox 检查。此时到达的 steering 使候选终态失效，先处理用户输入。

继续反馈只包含目标、当前缺口、原因码和下一步；作为带来源的控制参考进入后续投影，
不伪造用户说了“继续”，不插入假 tool call，不提升为额外用户授权。

### 防循环与执行上限

- 每段默认至多 100 次前台模型调用、60 分钟经过时间；数字仅为原型初值，待实验校准。
- 每次调用前扣本段次数；provider 失败同样计数。持续调用工具、不尝试结束也受上限约束。
- 工具安全边界检查时间；长操作沿用已有工具超时与取消。这是执行守卫，不是严格计费上限或精确实时抢占。
- 压缩调用、provider 内部重试和子代理用量单独计入可知统计，不假装被前台 100 次全部涵盖。
  没有准确计数/金额时明确未知；不为统计费用先改造全部 provider。
- 没有固定的拒绝次数上限：提前收尾会继续给出具体缺口，是否停止由用户决定。
  宿主只受既有工具/请求限制约束，不新增隐藏的自动暂停条件。
- 更严格的宿主/工具限制优先。Goal 不延长已有超时，也不强制自动重试失败工具。

## 13. 持久化：与消息同一提交，不再双写 sidecar

### 13.1 记录位置

沿用 [Message.provider_items](../src/protocol.rs) 的宿主元数据做法，在已有消息上保存：

```json
{
  "type": "kroma_task_control",
  "version": 1,
  "owner": "goal",
  "id": "host-generated-id",
  "revision": 2,
  "seq": 5,
  "status": "completed",
  "scope": {"archive_key":"host-derived","generation":123},
  "run_id": "host-generated-run",
  "data": {"summary":"...","claim":"done"}
}
```

示例省略检查轮次字段。控制记录与携带它的消息、压缩状态一起使用现有 append/checksum/fsync。
内存中的权威控制状态也只在 append 成功后切换；提交失败保留旧快照并进入 poisoned 状态。
不新增 Goal 文件、数据库或独立 WAL；原有会话 JSON/WAL 外层格式不变。

- 开始：原始用户命令消息 + 初始 running 快照一次提交，然后才发送模型请求。
- 检查点：工具结果 + 已校验的新快照一次提交；插件自身不得先写权威状态。
- 正常响应：在该响应的同次提交中保存必要的执行段统计，不逐 token 写状态。
- 完成：正常结束判断成功后，候选回答 + completed 快照一次提交。
- 失败/取消：现有失败/取消说明 + paused 快照一次提交，先补齐待定 tool 结果。
- 没有模型候选回答的有序暂停：写宿主来源的故障说明 + paused 快照，不复用上一条成功回答冒充本轮交付。
- 空闲时的 pause/cancel 等控制操作：写带明确宿主来源的控制说明消息，不启动模型。

宿主私有控制字段和原始执行记录不直接发给 provider；投影中只渲染当前需要的有限参考块。
该宿主命名空间只允许控制适配器写入；模型/provider 响应中的同名保留字段必须拒绝或剥离，
普通工具内容中的同名 JSON 不参与回放。不能因字段叫 kroma_task_control 就相信其宿主来源。
标准模型工具配对不变。完整历史/导出可保留元数据，面向 provider 的消息必须剥离其私有内容。
不借元数据存 provider continuation、伪造模型推理或新用户指令。
剥离仅针对新增的宿主私有类型并在投影副本上执行，不能删除全部 provider_items 或全部 kroma_* 元数据；
现有签名推理、图像、native tool continuation 与原始历史必须保留。

### 13.2 关键提交顺序

当前 Agent 会先保存回答再决定结束；Goal 路径必须调整为：

```text
拿到完整候选响应 → 正常结束判断 → 原子确认没有 steering 并封口
                 → 将候选响应及终态快照一次 append/fsync
                 → 发布 TaskControlChanged / FinalAnswerReady
                 → 发布原有 TaskFinished
```

若要继续，候选响应携带 running 快照与缺口说明正常保存，然后进入下一次请求。
若插件故障暂停，保存 paused，不把候选“已完成”文字当 completed。
流式文字在提交前只是草稿，宿主不能提前显示目标完成标记；原始文字不做不诚实的事后改写。

任何 append 失败都沿用 poisoned-session 规则：停止后续执行，不发布目标完成，重启后以有效 WAL 前缀恢复。
不增加“先宣布成功，再异步补存状态”的第二阶段。

### 13.3 回放与计数

载入时扫描一次权威消息，选择当前 scope 下最新的控制快照；请求期间使用内存缓存，
不每轮读取整份 WAL。检查事实从原始执行记录建立有界索引。

- running 遗留表示非正常中断：恢复为 paused 后再允许继续，不自动发送模型请求。
- 崩溃可能发生在模型已被调用但响应/计数尚未提交之间；跨段用量此时标为下界/未知，不能假装精确。
- 因为重启不自动续跑，resume 是用户对新段的显式授权。
- 缺少终态记录不根据最后一条 assistant 的措辞推断成功。
- 旧宿主不支持新能力就不能开启/恢复 Goal；不承诺把新控制语义透明降级成普通聊天。

## 14. 插件协议：有限、可校验、旧插件不受影响

### 14.1 请求上下文

仅向 task_control 所有者发送只读控制快照、真实命令来源和所需执行事实。
host 字段不接受同名模型工具参数覆盖。
为命令、控制工具和结束回调统一增加根级 control_context，含当前 ID/revision/seq/scope/status/checks/data 及只读用户来源；
start 时当前状态可为空。命令还带真实原始用户输入，宿主在提交时绑定其消息位置。
校验引用使用权威历史而非模型回传副本，插件无需访问整个 WAL。
线上字段固定为 control_context.user_sources: [{message_index, content, role?}]，来源只能是真实 user 输入；
命令请求的 user_input 是 slash 名称后的原正文，不是再次包含 /goal 的整条命令。
宿主仍在权威会话中保留完整原始命令，不能用插件生成的提示替换其来源。

### 14.2 命令/工具回复的控制建议

沿用 content/is_error，并给该能力的回复增加可选 `control`：

```json
{
  "protocol_version": 2,
  "request_id": 7,
  "content": "目标已准备",
  "is_error": false,
  "control": {"op":"start","base_seq":0,"data":{"summary":"修复登录"}}
}
```

控制回复只允许 start/resume/update。pause/cancel 属于宿主保留的真实用户动作，不增加进程往返；
没有直接写 completed 的操作，受阻暂停使用下节结束回调。
base_seq 回显请求当前快照的 seq；无当前控制状态时为 0。start 不指定新 ID，其他操作须回显既有 ID/revision；
owner/scope 从请求和 worker 身份绑定，不采信插件另给的新身份。
data 为更新后的完整插件数据而非任意 JSON Patch；可选 control.checks 提议当前完整检查计划，省略则继承。
is_error=true 时不接受控制效果。

- start/resume 只接受显式用户命令；宿主生成 ID、run_id 和来源身份。
- update 只接受所属控制工具的回复，且必须匹配请求的 ID、revision、seq 与 scope。
- start/resume 只由真实用户命令授权；模型控制工具仅能 update。
  运行中的用户 pause/cancel 立即走现有取消路径，插件没有阻止权。宿主把本次停止意图绑定到当前目标 ID，
  在取消说明的同次提交中分别记录 paused/cancelled，不先写暂停再靠异步通知猜测用户是否取消。
- 只有 content 或普通 JSON 文本中出现 `control` 不产生效果；必须来自正确 worker 的根级协议字段。
- 普通插件/V1 不获得控制权限，也不因为同名字段获得执行权；既有帧保持原行为。
- 模型无权自己构造此字段；工具结果 hook 不能篡改或创造内部控制建议。
- 无效模型工具参数是普通工具错误，可修正；所有权错误、协议损坏、过期控制提交不得产生部分更新。

### 14.3 正常结束回调

```json
{
  "protocol_version": 2,
  "request_id": 42,
  "type": "task_control",
  "name": "before_task_finish",
  "control_context": {"id":"...","revision":2,"seq":5,"data":{}},
  "arguments": {
    "facts": {"checks_satisfied":false,"checkpoint_basis_valid":false,"missing":["T1"],"finish_rejections":0},
    "candidate": {"has_content":true}
  }
}
```

content 中返回一个有界 JSON 决策对象：

```json
{"decision":"continue","reason_code":"MISSING_CHECK","feedback":"运行已登记的 T1，再更新检查点。"}
```

decision 为 finish/continue/pause；continue/pause 必须有可展示的原因。
回调只返回建议，不直接提交状态；宿主可以因用户输入或事实矛盾拒绝 finish。
请求总大小至多 1 MiB（为完整目标与用户原文留出空间），解码后的决策至多 4 KiB；feedback 至多 2048 字符，超限视为协议错误。
只传当前计划需要的事实，不发送整段对话、完整日志或额外的模型连接密钥/服务凭据。

回调默认 2 秒超时、可取消。超时、坏 JSON、崩溃、版本不兼容均暂停活动目标并说明原因，
不沿用记忆注入的 fail-open 行为，也不自动开第二个控制器。
没有活动目标的普通任务不调用此回调，插件失效也不能阻塞无关聊天。

### 14.4 一次性启动任务

命令回复产生 PreparedTask，而不是由插件调用 `Agent::run`，也不是向 follow-up 队列无限追加“继续”。
宿主一次消费准备结果，以原始用户命令/正文作为真实用户输入，附初始控制快照后启动正常任务。
启动前校验目标仍是同一会话、当前没有前台操作、准备结果尚未消费；失败不产生半活动目标。

新分发接口返回“文本回复或准备任务”。旧 CommandReply 构造与旧命令 API 保留；
不支持启动效果的旧分发入口必须明确报不支持，不能丢弃效果却显示目标已启动。
CLI/TUI/Desktop 统一接入新分发入口；它不得开启或消费用户原先暂停的 follow-up 队列。

## 15. 上下文与压缩

- 复用当前压缩器，原始用户消息、执行记录和控制快照仍在权威历史中。
- 每次模型投影只加入当前目标、当前 revision、验收点、检查计划、最近进展和必要缺口。
  不重复完整历史，不为生成这段参考另发模型请求。
- 使用显式来源标签表达控制参考；不能覆盖 system/developer 指令，也不能把工具内容提升成用户授权。
- 活动目标上下文纳入现有最终预算检查。它是执行所必需的内容，不能因普通记忆 pack 超时/截断而静默消失。
- 若压缩后仍容不下必要目标信息，暂停并报告上下文限制，不删掉用户条件继续执行。
- 成功检查点使目标参考失效并重建；利用现有 invalidates_context 通道，不能靠旧缓存判断完成。
- 压缩后看不到原始调用 ID时，模型从紧凑检查事实中取得引用；宿主以权威索引验证，不凭摘要补造成功记录。
- 实现中必须在普通请求、overflow 恢复、checkpoint 和 process-model 适配中测试私有字段的剥离。

## 16. 恢复、会话操作与插件生命周期

| 操作 | 规则 |
| --- | --- |
| 重启、进程退出、遗留 running | 解释为中断并暂停；已有工具结果不重放 |
| resume | 新 run_id、新检查轮次；保留要求与检查计划，通过事实不自动继承 |
| 普通换模型 | 保留目标；完成判断仍基于当前修订与事实，不把旧推理当新模型已确认 |
| 新会话 | 不带活动目标 |
| fork、rewind、undo | 新 scope/history generation；复制的旧记录仅参考，必须追加/解释为 paused，不能复活旧运行 |
| /clear、reset | 清空当前控制状态；不能让旧 WAL generation 恢复目标 |
| 删除/恢复/导出会话 | 状态随同一会话消息走，不再额外管理 Goal sidecar |
| archive 移动/身份变化 | 先暂停并重新绑定，不能自动接管另一个 archive 的 running 目标 |
| 插件禁用/卸载 | 目标不再自动推进；已有代码与会话记录不删除，展示 plugin_unavailable |
| 插件代码或数据版本改变 | 记录里的版本仅供诊断；数据兼容由插件校验，不因发版号变化锁死用户 |
| 子代理 | 不继承父控制状态；嵌套执行策略不会因父插件已启用而自动开启 |

scope 必须由 archive 身份和现有会话 generation 推导。创建分支/缩短历史时显式失效，而不只依赖路径比较。
若复制/缩短后的历史仍有完整目标来源，宿主为新 scope 创建新的目标 ID，保留要求但清除通过事实和完成声明，
仅以 paused 恢复并保留检查计划；若最新记录已结束（completed/cancelled）或原始用户输入已被截去，
则不恢复该目标。旧 scope 的记录只能作为历史参考，分支不会翻出更早的旧目标。
所有分支入口都要覆盖，不能仅在 UI 上禁止某个按钮。

## 17. 失败处理与不可省略的不变量

| 情况 | 行为 |
| --- | --- |
| 检查失败 | 当前模型可继续定位与修复；不自动重复同一命令 |
| 必要条件缺凭据/权限 | paused + 所需条件，不擅自开通服务 |
| 声明缺失、证据查不到、错 revision | 拒绝该次提交并说明缺口，可修正后重试 |
| 控制器不可用/坏协议 | paused，不降级成成功 |
| provider 错误 | 原有 failed 边界 + Goal paused；不增加隐式模型重试 |
| Ctrl+C/Stop | 取消当前 future，补齐未知结果，保存 paused；不走阻止结束回调 |
| WAL 失败 | poisoned，停止；不发布目标完成 |
| 工具 batch 中决定暂停 | 未执行项记录 not_executed/unknown，保持配对；不为填洞执行剩余副作用 |

必须成立：

1. 插件建议、模型声明、UI 通知都不是权威提交。
2. completed 快照与被接受的最终回答属于同一个持久化消息，不存在跨文件完成事务。
3. 候选回答已流式展示或仅有 assistant 消息，不代表 Goal 已完成。
4. 一次前台运行只发一次最终 TaskFinished，Goal 状态单独表达。
5. 封口后的晚到输入被拒绝或由宿主明确作为下一轮处理，不静默丢失。
6. 不确定的工具副作用永远不自动重放；恢复至多重核验，不保证外部副作用的 exactly-once。
7. 用户输入修改要求会失效旧声明，不能由旧验收点否决用户改口。
8. 无 Goal 时沿用普通执行路径，不能为了少数目标任务改变所有聊天的停止语义。

## 18. 实现文件与分阶段计划

### 18.1 计划新增/修改

| 位置 | 责任 |
| --- | --- |
| `examples/plugins/goal/plugin.toml`、`main.js` | 清单、JSONL 分发、纯 Goal 规则；运行时代码先集中一个 JS 文件 |
| 同目录测试与 README | Schema、规则、协议与用户说明；不拆空壳模块 |
| `src/task_control.rs`（拟新增） | 小型控制状态、事实索引、建议校验与回放；不实现 Goal 业务推理 |
| `src/plugins.rs` | capability、受限控制回复、唯一控制器、启动与结束适配 |
| `src/agent.rs`、`src/tools.rs` | 边界接入、原始事实、单次提交、取消与计数 |
| `src/protocol.rs`、投影相关代码 | 宿主元数据、恢复与 provider 剥离 |
| 命令与 CLI/TUI/Desktop 入口 | 一次性 PreparedTask 分发、运行中暂停、状态展示 |
| 现有测试、插件指南和 lifecycle 文档 | 回归与协议契约同步 |

这不是“两三个文件的小补丁”。代码主体可集中，但所有涉及的正确性边界都必须验证。
不为了减少表面行数把控制建议藏进字符串或把执行逻辑复制到三个宿主。
原始执行记录通过内部执行 outcome 传递，优先保持现有 Tool trait、ToolResult 构造与普通工具行为不变；
不能要求所有第三方工具为支持 Goal 强制升级，也不能从被 after-hook 改写后的结果倒推原始事实。

### 18.2 里程碑

1. **M0：最小可行原型**。假模型 + 假插件跑通 start → 一次正常执行 → 一次拒绝提前结束 → 完成；
   无真实网络/收费服务。先统计宿主改动和接口代价，重新确认架构没有膨胀。
2. **M1：闭合正确性**。真实 Goal 规则、原始事实、修订、同消息提交、恢复和故障注入全通过。
   M0 的不完整恢复或省略版 Schema 不能作为可用插件发布。
3. **M2：三宿主适配**。CLI/JSONL、TUI、Desktop 的命令、暂停、状态和队列行为一致。
4. **M3：对照验证与发布**。通过下节实验，再补文档、安装检查、启用/禁用/回滚说明。

不在编写本设计的过程中顺便部署不完整 Goal 插件，也不自动更改用户的现有插件设置。

## 19. 测试矩阵与对照实验

### 19.1 确定性测试

| 组 | 必须覆盖 |
| --- | --- |
| 命令 | 创建即执行一次；空输入；重复创建；暂停/继续/取消；新目标不静默覆盖运行中目标 |
| 检查点 | 必填、空占位符、大小限制、重复 ID、非法来源、过期 revision/seq、无活动目标 |
| 验收 | 虚构 ID、跨目标/修订引用、失败/未知结果、改写后的结果、旧消息无原始事实 |
| 新鲜度 | 先登记后执行；精确命令匹配；多检查同轮；任意普通工具失效；检查计划变更；resume 失效 |
| 用户优先 | streaming/gate/提交前到达 steering；新要求覆盖旧要求；停止不被回调阻止 |
| 提交 | 开始、工具、完成、取消各点的半写/完整写后崩溃；不凭候选回答推断完成 |
| 收尾循环 | 持续提前收尾时继续给缺口，不自动暂停；用户停止与显式 resume 各自成段 |
| 故障 | 进程崩溃、超时、坏 JSON、错 owner、错 scope、插件禁用、WAL poisoned |
| 会话 | 压缩、checkpoint、overflow、fork、rewind、undo、clear、移动、删除恢复、子代理 |
| 宿主 | 三入口同语义；前台 completed + Goal paused 不误显示；follow-up 队列不被接管 |
| 兼容 | V1/V2 旧帧、现有 tool 配对与取消、普通任务无控制 IPC、所有 provider 私有元数据剥离 |

故障注入须以真实 WAL 恢复验证，不只 mock 一个“已保存”的返回值。
测试以有界假模型为主；真实模型评估单独执行，不混进默认单元测试造成收费或不稳定。

### 19.2 三组对照

A：普通 Kroma；B：普通 Kroma + 更明确的目标/验收提示；C：Goal 插件。
相同模型、配置、初始文件和独立验收；每组从独立工作目录开始，不能共享前一组的修复成果。

任务包括：已有回归用例的 bug、小功能、长链路修改、设计交付、缺凭据的受阻任务和会提前收尾的任务。
先小样本多次试跑，失败分类后再扩大；不能凭一次成功就宣布胜出。

记录：

- 独立验收的真实完成率，而不是插件自报 completed 比例。
- 用户催促/纠正/补充条件的次数，以及完成前额外操作数。
- 错误宣布完成、错误暂停、无关扩展、重复检查和不必要权限请求。
- 模型请求、已知 token、总耗时、控制 IPC 开销、控制快照引起的 WAL 增量。
- 控制器代码/接口体积及对普通路径的影响。

### 19.3 发布门槛

确定性不变量全部通过；不得出现虚假持久化完成、用户中止失效或副作用重放。
C 必须相对 B 展示可重复的完成率或用户介入改善，且不能主要依赖明显更多的请求和重复劳动。
性能与费用差异如实报告，不提前编造收益百分比；没有增量收益就收缩或放弃该机制。
默认请求数、分钟数和收尾重试上限根据试验再定，不把原型初值当产品真理。

## 20. 审查问题的处理结论

| R0 问题 | R1 决定 |
| --- | --- |
| 用原生能力冒充最小插件 | 采用真实进程插件；通用控制边界有限且先做成本原型 |
| 模型自己判卷被包装成可靠验收 | 区分执行事实、模型判断和未验证项；外部验收衡量真实收益 |
| WAL + sidecar 双写 | 取消 sidecar；状态与对应消息同次提交 |
| 前台任务和目标状态混淆 | 保留原 TaskFinished，单独表示控制状态 |
| 用户改口与旧验收冲突 | 用户修订号、来源、旧声明失效，用户最新要求优先 |
| 不可执行的“可能写入”判断 | 明确登记检查 + 保守检查轮次，不解析 shell 猜副作用 |
| 主观“三次无进展” | 已删除自动暂停；停止由用户决定，不宣称语义停滞检测 |
| 没证明比普通模式更好 | 增加 A/B/C 对照和真实验收，收益不成立就不发布 |

## 22. 本轮优化（2026-11-09）

审查结论要求"保留持续执行能力，去掉不必要的验收官僚流程"。本次落地：

1. **取消强制填表**：启动不再生成验收点；检查点只需 `summary` + `claim`；验收点、检查、证据全部可选，
   模型可以随时修正自己的列表，不再需要用户先追加修订。
2. **取消无差别失效与重跑**：检查可在执行后登记，执行事实保留在整段目标内；只有完成声明会因新的工具操作失效。
3. **取消隐藏暂停**：删除"连续三次拒绝收尾即暂停"；用户停止是唯一的硬边界。
4. **用户可重新打开目标**：`resume` 对暂停、已完成、已取消都生效；分支永不复活已结束目标。
5. **修复正确性缺陷**：证据 ID 由宿主核对；后端元数据在入库前剥离；分支保留检查计划；插件版本不再锁死恢复；
   取消只写一次终态。
6. **修复可扩展性问题**：用户来源按目标精确保存（不再扫全历史、不再 64 条/8 KiB 截断）；
   投影完整保留用户原文与全部条件（不再 600 字符截断）；请求上限提升到 1 MiB。
7. **三端一致**：CLI 运行中输入 `/goal pause`/`/goal cancel` 直接走宿主停止路径；
   Desktop 从持久化快照恢复目标并区分"目标暂停"与"任务完成"。
