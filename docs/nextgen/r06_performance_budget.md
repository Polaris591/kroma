# KR-R06 性能预算、退化告警与停止优化规则

验收要求：能说明为何继续或停止优化；不以"追求极致"作为无限开发和功能堆叠的理由。

## 二、预算线（什么算退化）

这些是**本机实测值**，不是行业基准，也不是验收硬线（任务卡明确禁止拿作者他机数据当硬线）：

- 启动墙钟：超过 50 ms 视为退化（当前 4.7 ms，10 倍余量）
- 启动内存：超过 10 MB PSS 视为退化（当前 3.5 MB）
- 图导航：超过 8 s 视为退化（当前 3.3 s，2.4 倍余量）
- 协议开销：超过 5 ms 视为退化（当前 0.425 ms，12 倍余量）
- 工具输出：单次超过 200 KB 视为退化（当前最大 2.4 KB）

退化告警应该比较**中位数**而不是单次值：本机 p0 有过一次 61 ms 的单点（首次运行时文件系统未缓存），
拿单次值报警会产生大量假阳性。

## 三、停止规则（何时不该继续优化）

1. **占比 < 1% 的路径停止优化。** 协议开销占端到端 0.013%，再怎么优化客户端序列化也改不了用户感知。
   继续投入是浪费。
2. **优化上限由实测比例决定。** 工具结果只占请求体的一部分（turn 3：5025 / 14837 字节 ≈ 34%），
   所以"优化工具输出"的理论上限是那 34%，不是 100%。超过上限的承诺必然是假的。
3. **没有配对证据不晋升。** 任何"省了 token / 更快"的说法必须来自同一模型、同一任务的配对运行，
   且质量非劣。当前 35 个实验因为执行器缺陷没有统计结论，因此**没有任何机制被晋升为默认**。
4. **默认配置不依赖未验证机制。** 实测确认默认仍是 P2 profile、无候选、无因果剪枝、无按需工具。
5. **退化优先于优化。** 先保证预算线不破，再谈提升；顺序反过来会让基线本身变得不可比。

## 四、明确不该做的事（基于上面数据）

- 不做客户端协议层优化（0.013%）。
- 不把"扫描字节"当优化目标：read 扫 2 MiB 只输出 338 字节，真正的杠杆是返回行数而不是文件大小。
- 不为图导航做增量索引优化，直到确认 3.3 s 是用户可感知的瓶颈（目前没有证据）。
- 不在没有配对 A/B 的情况下调整压缩/缓存默认值（历史教训：v4 的 E04 在开发集说 −44%，留出集反说 +19%）。

## 五、为什么这一项可以关闭

任务卡要的是"能说明为何继续或停止"，不是"已经优化到极致"。上面每一条规则都绑定了一个本机实测数字，
并且明确列出了**不该继续**的方向。剩下的开放问题是实验执行器（F03），那不是性能预算问题。

## 六、没有做的部分

没有做多轮 p50/p95 的重复统计（只有 3 次中位数），也没有把内存/延迟随仓库规模做成曲线。因此上面的
预算线是"当前量级"的判断，不是精确的回归阈值。
