# KR-I01 工具 I/O 成本与 token 消耗的分离

验收要求：产出不包含模型延迟的本地基线与有模型任务结果，**不将扫描字节直接等同 token 消耗**。

## 一、本地基线（无模型，来自 KR-R01 的测量）

| 场景 | 中位数 | 树 PSS |
|---|---|---|
| p0 `kroma --version` | 4.70 ms | 2.2–3.5 MB |
| p2 `acp` + `workspace.graph`（本仓 560 文件） | 3296 ms（init 11 ms） | 75 MB |
| p3 `acp` + `workspace.graph`（生成小树） | 245 ms | 25 MB |
| p4 四个并发 `acp` 会话 | — | 269 MB |

这部分不含任何模型调用，是纯进程与索引成本。原始数据：`r01_local_baseline.json/report.json`。

## 二、有模型的任务结果（来自 live canary）

同一份 `RequestCompositionObserved` / `ModelRequestCompleted` 里同时记录了请求字节与
provider 报告的 token，可以直接对照：

| 日志 | turn | tool_result 字节 | 请求体字节 | input token | 字节/ token |
|---|---|---|---|---|---|
| k06-live-mcp | 1 | 0 | 9472 | 1911 | 5.0 |
| k06-live-mcp | 2 | 301 | 9811 | 2025 | 4.8 |
| k06-live-mcp | 3 | 5025 | 14837 | 3143 | 4.7 |
| k06-live-mcp | 4 | 5124 | 14958 | 3207 | 4.7 |
| e05-canary | 1 | 0 | 9441 | 1904 | 5.0 |

## 三、结论

1. **字节不是 token**：请求体 9472 字节对应 1911 token（5.0 字节/token），而工具结果增加
   5025 字节只增加约 1232 input token（4.1 字节/字节）。任何把"扫描了多少字节"直接当成
   "花了多少 token"的换算都是错的。
2. **工具结果只占请求体的一部分**：turn 3 的请求体 14837 字节里，工具结果是 5025 字节，
   其余是静态前缀（约 9.4 KB）与历史。所以优化工具输出能省的上限由这个比例决定，而不是由
   文件大小决定。
3. **本地基线与模型结果必须分开报**：p2 的 3296 ms 是索引成本，canary 的 ttft 3336 ms 是
   模型成本，两者数量级接近但完全不同源。把二者相加当成"端到端"会误导。

## 四、四个工具的输出成本（同一棵 201 文件树，无模型）

测试：`t06_bounded_io::the_four_file_tools_have_measured_output_costs`。
树：200 个 ~30 字节的 `f*.rs` + 一个约 2 MiB 的 `big.rs`。

| 工具 | 参数 | 输出字节 | 耗时 |
|---|---|---|---|
| read | `big.rs` offset 1 limit 10 | **338** | 108.77 ms |
| grep | `pattern="fn f1"` | 2418 | 3.81 ms |
| find | `pattern="*.rs"` | 1524 | 2.43 ms |
| ls | `path="."` | 1524 | 0.72 ms |

`read` 这一行就是本任务的核心事实：**扫描了约 2 MiB，模型只看到 338 字节**。扫描成本与输出
成本差三个数量级，把它们混为一谈会得出完全错误的优化方向（例如"减少读文件大小"而不是
"减少返回行数"）。耗时只作记录、不作断言——共享 CI 机器上的墙钟不是代码属性。

## 五、仍然没有做的部分

没有做多轮重复的耗时统计（p50/p95），也没有把四个工具的耗时与仓库规模做成曲线。上面的
单次测量足以证明输出成本的量级差异，但不足以支撑"某个工具更慢"的性能结论。
