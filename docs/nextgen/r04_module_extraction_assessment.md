# KR-R04 按不变量提取大模块：评估结论是不拆

验收要求：重构不改变可观察契约；**没有降低故障隔离或维护成本的证据则不继续拆**。

## 候选

| 文件 | 行数 |
|---|---|
| `agent_loop.rs` | 5636 |
| `bench.rs` | 4869 |
| `surface/repl.rs` | 2867 |

最大函数：`run_provider_turn` ~893 行，其后是 `run_subagent_batch` ~549、`execute_tool_batch` ~527、
`handle_completion_turn` ~465。

## 评估

`run_provider_turn` 内部确实有可辨认的阶段：预算记账 → 路由 → 窗口检查 → 投影 → task-state 落盘 →
工具集构造与冻结 → 发包前 reserve → 请求构造 → 发送 → 结算。**但这十个阶段是严格串行且共享状态**：
每一步的产物是下一步的输入（`projected`、`request_tools`、`final_tool_schema_bytes`、`reserve_amount`、
`token_reservation`），而且都读写 `state`、`logger`、`self`。

拆成独立函数的代价是把这些状态打包成参数或引入一个新的上下文结构体，等于把"隐式共享"变成"显式传递"。
这不是免费的：本轮修 KR-B01/B02/B03/B04 时，正是因为这几步的顺序和共享状态被拆散过（估算用静态工具集、
检查用另一套口径），才产生了一整类 bug。把它们收拢在一个函数里、按顺序读一遍就能验证"工具集先定后测"，
这对这类代码是**特性而不是缺陷**。

## 收益证据

- **故障隔离**：拆不拆都是同一个 `AgentRunner` 调用栈，拆开不会让任何一步的失败变得更容易隔离。
- **维护成本**：函数已有 386 行注释把每个阶段标出来；本轮 6 个修复都在这个函数里完成，没有出现"找不到位置"。
- **测试**：1311 项测试覆盖行为不覆盖结构，拆分的正确性只能靠"测试仍全绿"，那是必要不充分条件。

没有任何一项证据表明拆分能降低维护成本或改善故障隔离。按任务书原文，**不继续拆**。

## 如果将来要拆，前提是什么

先有"某个具体 bug 因为函数太长而漏看"的记录（比如修错位置、漏改一处口径），再用那个 bug 作为拆分理由，
拆完用它做回归。当前没有这样的记录。

## 已做过的拆分类工作（对照）

不是"拒绝一切重构"：`surface.rs` 已拆成 12 个模块、安全原语已收口到 `secure_fs`、`run_inner` 已从
1104 行降到 23 行。这些都有明确的不变量边界（surface 按协议、安全原语按"无 follow 的路径操作"）。
`run_provider_turn` 的阶段边界是"顺序依赖"，不是"不变量"，性质不同。
