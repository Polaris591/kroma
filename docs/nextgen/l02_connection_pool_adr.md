# ADR: 连接池（KR-L02）

状态：**候选，默认关闭**（未实现）
依据：L01/KR-R01 的本机测量

## 背景

`provider/transport.rs` 的 `send_request` 每次请求都新建 TCP 连接（`TcpStream::connect` 到解析后的地址）
并在 HTTPS 上做一次完整 TLS 握手，然后写 `Connection: close`。没有连接复用。

## 测量（本机，已有数据）

- loopback 上一次完整请求（connect + 序列化 + 写 + 读 + 解析）中位数 **425 µs**（KR-L01，5 次）。
- 远端首 token 中位数 **3336 ms**（KR-E03/E05，chat-completions canary）。
- 因此客户端协议层占端到端 **0.013%**。

## 分析

连接复用的理论收益上限就是那一次握手 + 一次 connect。在 loopback 上它是 425 µs 的一部分；在真实
远端上它被网络 RTT 与推理时间淹没（3336 ms 里占不到 1%）。所以：

1. **吞吐型场景**（同进程内连续几十个请求）收益可测，但需要先有那样的负载。
2. **延迟型场景**（一次任务几轮到几十轮，轮间还有工具执行与人工审批）收益接近零。
3. 代价是真实的：必须处理 stale connection（服务端已关而客户端不知道）、TLS 会话复用与证书重检、
   代理/CDN 的连接上限、以及在 `Connection: close` 语义下的重试归属。这些都属于"为 0.013% 引入
   新的正确性风险"。

## 决策

保留为候选，**默认关闭**，不实现在默认路径上。满足验收的"没有测量就只保留候选关闭默认"——
测量有，结论是收益低于风险。

## 何时重新评估

出现以下任一情况时再看：(a) 有单进程连续数百请求的真实负载并测出握手占比 >5%；(b) 上游要求
HTTP/2 或连接复用以获得配额；(c) 引入成熟 HTTP 客户端（如 hyper/reqwest）时顺手获得，而不是自己写池。

## 明确不做的

不自己写连接池状态机；不为了"看起来现代化"而引入复用；不在没有 stale-connection 测试的情况下
打开复用。
