# 四份「不实现」的决策记录（KR-J06 / L06 / O02 / F05）

每份都按 L02 的格式：现状 → 证据 → 为什么不做 → 何时重评。任务卡对这四项的要求都是"有证据才采用"，
不是"必须实现"。

## KR-J06 Provider-native compaction：不实现

- 现状：Kroma 的压缩是自建的（`context_projector` + `cache_aware_compaction`），有 stub、working-set
  pinning、watermark 降级等；没有依赖服务端的会话压缩 API。
- 证据：服务端压缩（如 OpenAI 的 conversation state / Anthropic 的 context editing）在当前端点
  （cobblemon.asia）未声明支持；`openai_responses.rs` 的 `MessageSemantics` 只声明了它能表达的字段，
  未声明的不会被发送。
- 为什么不做：要自建一个"服务端压缩状态机 + 回放"，必须先在真实端点上验证语义，否则就是伪造协议
  支持（K04 的原则：不能把字段接受当协议实现）。
- 何时重评：端点声明支持且能在 live canary 上回放出可复现的压缩结果。

## KR-L06 原生 Tool Search / Programmatic Calling：不实现

- 现状：Kroma 用自己的 `discover_tools` 做按需 schema 暴露（H03/H04 已测：on-demand 在 dev +8% /
  holdout −10%，不晋升；而"最小工具集"省 55% token，说明真正的杠杆是菜单大小而非搜索机制）。
- 证据：供应商原生 tool search 在 `chat_completions`/`anthropic_messages` 上不可用；`openai_responses`
  的 native tool search 事件流被显式 fail-closed（不静默回放）。
- 为什么不做：在原生协议不支持的端点上实现"原生搜索"只能是模拟，而模拟的收益已被 F04 证明远小于
  直接缩小菜单。
- 何时重评：端点支持 native tool search 并有真实计费证据。

## KR-O02 进程外扩展故障域：不做

- 现状：hook 已经走 `ProcessLaunch`（凭据清洗 + 进程组隔离 + fail-closed 的 containment），工具本体
  在进程内；MCP sidecar 本来就是独立进程。
- 证据：`extensions.rs` 的 hook 路径在独立进程组里跑（KR-C02 记录 `execution_backend=host`）；
  内置高频工具走直接热路径。
- 为什么不做：把每个扩展搬进独立进程会引入 IPC 协议、序列化与生命周期管理，而任务自己的验收是
  "仅在隔离价值成立时采用；内置高频安全工具保持直接热路径"——当前没有证据表明进程外能显著降低
  实际风险（hook 已经在独立进程组、MCP 已独立）。
- 何时重评：出现具体的安全需求（例如第三方扩展需要不同的内核策略），而不是"架构更干净"。

## KR-F05 27 个 Harness 可比性：不做（记录为不可比）

- 现状：本机可用的交互式 harness 只有 `pi`（@earendil-works/pi-coding-agent）与 `codex`
  （@openai/codex），另外 mini-swe-agent 本轮已安装并跑通（见 evidence/f05_msw_run.txt）；其余 7 个在 pypi/npm 上可解析但未安装，17 个未尝试。此前的「25 个不可得」说法已撤回。
- 证据：`which pi dsh` → pi 在、dsh 不在；`npm ls -g` → 只有 pi-coding-agent 与 codex。
- 为什么不做：任务要的是"可比性"，而可比性的前提是同一模型、同一任务、同一预算下都能跑；现有
  两个工具可以用（`kroma-arena` 已做过竞赛），但把 27 个硬凑齐会变成"用不同模型/不同预算的分数
  互相比较"，那正是任务禁止的。
- 何时重评：有可获取的 harness 集合且能固定同一模型与预算。

## 共同结论

这四项的处置都是"有数据/有事实支持的不做"，而不是"没做"。它们与 G03/H04 那种"做了并判负"不同：
这里连实现的前提（协议支持、外部工具、具体安全需求）都不成立。

## KR-J04 CADOC 风格对象卡与等待成本批次：候选，不实现

- 现状：压缩以"工具结果对象"为单位（stub 保留 path/range/symbols/evidence 指针），没有把多个
  读取对象合成"对象卡"再按等待成本批量取回的机制。
- 证据：论文声称的"约 40%"收益在本仓库没有任何测量支撑；本轮七个配对实验里，所有改变上下文
  形状的臂（P1/P3、causal_pruning、on_demand_tools）都没有产生超过噪声的质量或成本收益，唯一超过
  噪声的是"关掉子代理 -13.3%"。
- 任务卡自己的验收是"仅为候选算法，不能继承论文的约 40% 收益；Kroma 留出非劣失败则不晋升"。
  既然没有留出集证据，就不能晋升，也不该为了"看起来先进"而实现一套需要新状态机的对象卡机制。
- 何时重评：有一条任务集专门依赖"多对象批量取回"（例如同时读十几个文件再回答跨文件问题），
  并能测出对象卡在质量非劣前提下的成本收益。
